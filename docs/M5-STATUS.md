# M5 进度：候选池接入

设计第 5.1 节：**候选池以攻略知识库为主、高德搜索补全**（Q27）。
验收条件是「打开城市看到的是网友推荐而非一片 POI」。

---

## 一、验收条件的现状

**达成了。** `#/cities/{adcode}` 打开就是网友写过的地方：

- 每条候选的主体不是「名称 + 评分 + 距离」，而是**打卡建议与避坑指南本身**
  ——原文照登，带置信度与独立来源数
- 打卡与避坑分开排，不混成一段：「值得去」与「注意什么」是两类信息
- 来源看得见：`knowledge`（网友真的写过）与 `amap`（只是地图上有）
  在界面上是两种说法，整页文案都会跟着换
- 覆盖度说实话：数据还少时说「够不上支撑一次完整的规划」，
  而不是让空池子冒充「这座城市没什么可去的」

真实数据上（5 篇素材）：西安 5 个地方、南京 4 个、北京 1 个。
入口在行程页的城市名上——读到「西安 3 天」时，下一个问题就是
「西安有什么可去的」。

## 三、还没做

### 1. 接进排程流水线（设计 5.2 的「景点搜索」环节）

现在候选池只是**展示**出来了，还没有接进 `third_party/floattrip` 的
景点搜索环节。设计里说「排程不得引入候选池之外的景点——这条封闭世界约束
沿用 FloatTrip，并由复审环节硬性检查」，这一半还没动。

### 2. 已对齐的结论不会跟着对齐算法一起变好（**现在是用户可见的**）

M3 就记过这条：`align_pending` 只处理待办，一条待办解析之后就不会被重新检查，
**对齐算法的每一次改进都只对新数据生效**。M4 改了 ADR-0009 的爬链规则
（祖先只是容器时不归并），于是这个问题变得看得见了：

```
兵马俑的 7 条结论 → B001D09OYW  秦始皇帝陵博物院     （旧规则归并的结果）
兵马俑的预约规则 → B0FFGXMLTU  秦始皇兵马俑博物馆   （新规则的结果）
```

两者是父子关系（`B0FFGXMLTU.parent = B001D09OYW`），**但它们是两行**。
后果直接摆在界面上：

- 城市页的「秦始皇帝陵博物院」卡片有 7 条网友结论，**却没有预约提醒**
  （规则在另一行上）
- 行程页的兵马俑有预约提醒，**却挂不到任何结论**（M5 的候选池取不到）

需要的是一个**重新对齐**的工具：按 subject_name 重跑一遍对齐，
对不上当前 `poi_id` 的报出来（`--apply` 才改），改完重算独立来源数。
这是一次不可逆的数据迁移，得先看清楚要动什么再动。

### 3. 攻略结论挂载到天项与卡片

设计 5.4 说硬约束注入 prompt、软经验生成后挂载（ADR-0001 的第二次生效）。
天项旁边显示「这里有什么要注意的」还没做。

### 4. 天项与候选的对齐仍是两套

行程里的天项来自引擎的高德搜索，候选池来自知识库。两边都过 M3 的对齐，
但**没有一次跑在同一条口径上**——上面兵马俑那条就是它的一种表现。

## 四、一条观察：第二层归组的失效在界面上看得见了

西安那两个地方（陕西历史博物馆）的打卡建议里同时出现：

```
陕西历史博物馆免费参观但必须预约。
陕西历史博物馆免费但必须预约，官方公众号提前三天预约，每天早上八点开始抢。
```

这两条来自两篇不同的文章（西安原文与它的逐句改写），说的是同一件事，
但 `merge_claims` 没能把它们并起来——因为 M3 实测过：
逐句改写的两篇**精确结论指纹交集为 0**（归一化把数字改写了）。

结果是界面上出现了两条「待验证的个例（只有 1 个来源）」，
而它们其实**是两个独立来源**，本该合成一条「2 个独立来源」。

**这正是 M3 那条负面结论的用户可见后果**：不是抽象的指标不好看，
而是用户会看到同一句话说两遍，而且每一条都被标成「只有 1 个来源」——
本该更可信的信息，看起来反而更不可信了。
