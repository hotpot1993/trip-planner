# M5 进度：候选池接入

设计第 5.1 节：**候选池以攻略知识库为主、高德搜索补全**（Q27）。
验收条件是「打开城市看到的是网友推荐而非一片 POI」。

---

## 一、验收条件的现状

**达成了。** `#/cities/{adcode}` 打开就是网友写过的地方：

- 每条候选的主体不是「名称 + 评分 + 距离」，而是**打卡建议与避坑指南本身**
  ——原文照登，带置信度与独立来源数
- 打卡与避坑分开排，不混成一段：「值得去」与「注意什么」是两类信息
- 来源看得见：`knowledge`（网友真的写过）与 `amap`（只是地图上有）
  在界面上是两种说法，整页文案都会跟着换
- 覆盖度说实话：数据还少时说「够不上支撑一次完整的规划」，
  而不是让空池子冒充「这座城市没什么可去的」

真实数据上（5 篇素材）：西安 5 个地方、南京 4 个、北京 1 个。
入口在行程页的城市名上——读到「西安 3 天」时，下一个问题就是
「西安有什么可去的」。

### 软经验挂载（设计 5.4）

设计里的分层是：**硬约束注入 prompt**（开放时间、闭馆日、放票日、是否需预约），
**软经验生成后挂载**（避坑指南与打卡建议原文）。理由是后者不注入，
LLM 就无法把它们当成自己写的内容混进行程正文——编不出
「我在故宫拍到了没人的太和殿」。

两条取舍：

- **不产生任何新内容**，只把知识库里已有的原文贴上去，一个字都不改。
  任何转述都会让它从「证据」变成「我们的说法」。
- **不铺进时间轴的正文**，而是「几个标记 + 展开」。时间轴的价值是可扫读：
  几点、去哪儿、怎么走；整段攻略铺进去，扫读就没了。所以是
  「3 避坑 · 6 打卡」这样一个小按钮，点开才读原文。

真实行程上实测：4 个天项挂上了软经验（夫子庙 1 避坑、老门东 1 打卡、
兵马俑 2 避坑 · 5 打卡、陕历博 3 避坑 · 6 打卡）。

## 三、这一轮修掉的

城市页一打开就露馅了两件事，都是它连带抓出来的。

### 1. 已对齐的结论不会跟着对齐算法一起变好——**已修**

M3 就记过这条：`align_pending` 只处理待办，一条待办解析之后就不会被重新检查，
**对齐算法的每一次改进都只对新数据生效**。M4 改了 ADR-0009 的爬链规则
（祖先只是容器时不归并）之后就变成看得见的错误了。

新增 `ls align recheck [--apply]`：把库里每条提及按现在的算法重跑一遍，
报出落点变了的那些，人看过之后才搬。真实库上跑出 **4 条提及、11 条结论**，
而且**全是同一类**——旧规则把它们归并进了容器：

| 提及 | 旧落点 | 新落点 |
|---|---|---|
| 兵马俑（7 条） | 秦始皇帝陵博物院 | 秦始皇兵马俑博物馆 |
| 中山陵（2 条） | 钟山风景名胜区 | 中山陵景区 |
| 明孝陵（1 条） | 钟山风景名胜区 | 明孝陵景区 |
| 老门东（1 条） | 夫子庙秦淮风光带 | 老门东 |

界面上的后果很具体：城市页那张「钟山风景名胜区」卡片里装着中山陵与明孝陵的
结论，而**「中山陵要预约」被写在了整个钟山景区名下**——打算去明孝陵的人
会以为要预约钟山。已 `--apply` 搬完并重算独立来源数。

搬的时候要确认目标实体真的在库里：`claim.poi_id` 有外键，
而对齐认定不等于已入库。

### 2. 「要预约，但官方没公布放票口径」被显示成「没有预约信息」

搬完兵马俑之后发现的：城市页那张卡片上什么都不显示。
`CandidateOut` 只有 `booking_days` 与 `booking_time`，
而兵马俑那条规则两个都是 `None`（官方确实没公布）——
于是「必须预约」被渲染成了「不用管」。

**这正是这个项目最怕的失败模式**，而且是我自己写的新代码引入的。
现在 `CandidateOut` 带上 `booking_required`，三种状态分得开：

| 情况 | 显示 |
|---|---|
| 有规则，要预约，有口径 | 需预约，提前 5 天 17:00 |
| 有规则，要预约，**官方没公布** | 需预约，放票口径以官方为准 |
| 有规则，不需要预约 | 不需要预约 |
| **没有已复核的规则** | 什么都不显示（是「不知道」，不是「不需要」） |

教训与 M3 的「算不出来 ≠ 0」是同一条：**一个数字的缺失不等于一件事的缺失**。

## 四、还没做

### 1. 接进排程流水线（设计 5.2 的「景点搜索」环节）——**已完成**

做法是**运行时替换**：`planning/nodes.py` 里那一句是模块级导入

    from ..planning.helpers import fetch_city_spots_async

而节点调用它时走模块全局，所以在 `lushu/engine/pool_search.py` 里替换掉
`nodes.fetch_city_spots_async` 就够了——`third_party/` **一个字节不动**
（ADR-0005 的隔离由 `tests/test_architecture_boundaries.py` 把守，那条规则也
决定了这套代码必须住在 engine 层，而「池子里有哪些地方」由 services 层以
领域对象喂进来：engine 只认 domain，不认识我们的表）。

替换之后的行为就是设计那句话的字面意思：

1. **池子在前**（`max_spots` 是硬上限，排在后面的会被截掉，所以在前＝先被看到）；
2. **高德补全**，同名的去重（池子里的地方大多也搜得到）；
3. **池子没覆盖的城市原样走原路**——游客去一座没人写过攻略的城市时，
   行为与从前完全一样。每次规划都显式设定一次，状态不在两次规划之间残留。

真机跑过（南京，30 个）：

```
 0. 中山陵景区      rating=4.9     ← 池子
 1. 南京博物院      rating=4.9     ← 池子
 2. 夫子庙          rating=None    ← 池子
 3. 明孝陵景区      rating=4.8     ← 池子
 4. 老门东          rating=4.8     ← 池子
 5. 夫子庙中心广场   rating=4.2     ← 高德补的
 6. 永利广场        rating=4.3
 7. 莲花广场        rating=4.5
 …
```

后面那一串「广场」正是设计里说的「一片 POI」——而它现在排在网友真的写过的
五个地方之后。

**端到端跑过一次真规划**（「去南京玩两天，看看有历史感的地方」，2 天）：排出来的
5 个景点里 **4 个是池子里的**（中山陵景区、明孝陵景区、南京博物院、老门东），
第 5 个是「夫子庙秦淮风光带」——注意它**不是**池子里那个「夫子庙」，而是高德补
上来的另一个 POI。这正是下面那条问题的实际后果。

### 2. 池子条目不受评分门禁管——**已做**

引擎拿到景点清单之后有一道 `filter_by_rating`，**评分缺失一律不达标**。那道门禁
的意图是滤掉高德搜出来的噪声（评分缺失的往往是个广场、停车场、上车点），
但池子里的地方不是「高德搜出来的」——它们是网友真的写过的地方，评分缺失只是
高德没给（实测**夫子庙就没有**）。拿滤噪声的规则去滤已经认定过的条目，
是**判据用错了对象**。

于是把节点也换了（`engine/pool_search.py` 的 `_pool_exempt_node`）：池子在前、
池子条目不受门禁管、高德那部分照旧受管。

**只换搜索函数是不够的**——第一版就是这么做的，真机跑出来才发现：门禁在**节点**
里，而 `graph.py` 在模块级 `from ...nodes import attraction_search_node`，
自己另持一份引用。结果池子条目进得了清单、过不了门禁，排程拿高德的同名变体顶上。
现在两处绑定一起换，并且**只换一个函数**：节点自己调池子、自己调高德、自己决定
谁受门禁管——两件事在一处，就不会再出现「搜索换了、门禁没换」这种一半的状态。

真机验证（节点直跑，南京）：

```
景点搜索：候选池 5 个（不受评分门禁管） + 高德 29 个（rating≥4.0 保留 24，滤掉 5）= 29 个
   中山陵景区 4.9 / 南京博物院 4.9 / 夫子庙 None / 明孝陵景区 4.8 / 老门东 4.8 / …
```

五个池子条目全在，包括没有评分的夫子庙。

**顺带看出来的下一件事**：清单里现在有**三个夫子庙变体**（池子的「夫子庙」、
高德的「夫子庙秦淮风光带」与「南京夫子庙」）。池子条目排在前面是我们能做的，
但**LLM 最终挑哪一个不由我们决定**——实测它挑过带评分的那个同名变体。
真正管用的是下一步：**收紧封闭世界**（池子有货时就只让 LLM 从池子里选），
那才是设计 5.1 那句话的完整版本。

顺带补了一处数据：`pool_pois` 会把缺失的评分用高德的详情补上并**写回库里**
（缺评分是现状不是错误，查不到就保持原样）。不补的话，池子里没评分的地方
连进清单的资格都没有。

先做的**如实报出来**那一半仍然有用，不要撤：`GET /api/trips/{id}/coverage`
与行程页上的一行字——「行程里 7 个景点，4 个有网友写过，3 个只是地图上有」，
并点名列出那 3 个。封闭世界约束（「排程不得引入候选池之外的景点」）现在**可以
收紧了**：搜索已经由池子驱动，剩下的是「引擎可能仍然从高德补的那部分里选点」，
那是下一步。

### 3. 天项与候选的对齐仍是两套——**已修**

行程里的天项来自引擎的高德搜索，候选池来自知识库。两边都过 M3 的对齐，
但**没有一次跑在同一条口径上**。覆盖检查把它算了出来：

```
中山陵（行程引用 B000A8UIN0）  ←→  中山陵景区（结论挂在 B0FFHVEECG）
明孝陵（行程引用 B000A8UIN1）  ←→  明孝陵景区（结论挂在 B0FFFFKG55）
西安城墙（行程引用 X000A8UIN0） ←→  B001D0WP6V（M2 的占位 id → 真高德实体）
```

同一个地方，两行实体。上一轮的 `recheck` 把**结论**搬到了新实体上，
但**行程的天项**还指着旧实体，所以那两条结论在行程上完全看不见。

修法：`recheck` 现在把**两类引用一起收、一起搬**——

- `stale_subjects` 除了 `claim.subject_name`，还收 `day_item.title`
  （只算 `kind='poi'`；餐饮不参与实体对齐）
- `apply_plans` 除了 `claim.poi_id`，还改 `day_item.poi_id`
- `day_item.title` **不动**：那行字是人看到的景点名，与它指向哪个实体是两回事
- 目标实体没入库时**顺手写进去**——「重跑一遍对齐」本来就该有和跑对齐
  一样的效果，否则会撞上先有鸡还是先有蛋：实体没入库，引用就搬不过去

已应用：搬了 5 个行程天项。**覆盖从 4/7（57%）升到 6/7（86%）**——
中山陵与明孝陵的结论现在在行程上看得见了。

剩下那 1 个（西安城墙）是真实的：没有任何素材提过它，它是引擎排进来的。
那正是覆盖检查要让人看见的东西。

## 五、一条观察：第二层归组的失效在界面上看得见了

西安那两个地方（陕西历史博物馆）的打卡建议里同时出现：

```
陕西历史博物馆免费参观但必须预约。
陕西历史博物馆免费但必须预约，官方公众号提前三天预约，每天早上八点开始抢。
```

这两条来自两篇不同的文章（西安原文与它的逐句改写），说的是同一件事，
但 `merge_claims` 没能把它们并起来——因为 M3 实测过：
逐句改写的两篇**精确结论指纹交集为 0**（归一化把数字改写了）。

结果是界面上出现了两条「待验证的个例（只有 1 个来源）」，
而它们其实**是两个独立来源**，本该合成一条「2 个独立来源」。

**这正是 M3 那条负面结论的用户可见后果**：不是抽象的指标不好看，
而是用户会看到同一句话说两遍，而且每一条都被标成「只有 1 个来源」——
本该更可信的信息，看起来反而更不可信了。
