## 一、为什么置信度呈现不是「加个徽章」

设计第 4.5 节：

> 一条结论只有在同时满足三件事时才能进入攻略知识库：有原文证据、已对齐到 POI、
> 独立来源数已计入。置信度由独立来源数决定，多源的为高置信，单源的标为待验证个例。

「**标为**待验证个例，而不是丢弃」——这句话把「呈现」变成了必须做的事：单源经验
仍然展示，但**必须让读的人看得出它是单源**。M5 的城市页与行程页做到了这一点，
但漏掉了这份项目里最该有它的那个地方。

## 二、置信度呈现——**已做**

### 1. 路书原先根本不带置信度

`roadbook_render._item` 把结论一律平铺：

```html
<li class='av'>避坑 · 中山陵陵园很大，从停车场走到台阶下就要二十分钟，建议穿运动鞋。</li>
<li class='hl'>打卡 · 中山陵免费但需要预约。</li>
```

`RoadbookItem.highlights` 里只有一个字符串，来源数在装配时就丢了。于是
「三个人都这么说」与「一个人这么说」在这份**带上路**的文件上长得一模一样——
而它正是断网时唯一的依据：在路边低头看的人，没法回主项目查这句话是谁说的。
区分这两件事是整个信任模型存在的理由（Q34、ADR-0008），**最需要它的地方反而缺席**。

现在 `domain/roadbook.RoadbookClaim` 带着独立来源数，渲染成每条后面的一句：

```html
<li class='av'>避坑 · 夫子庙晚上人多，节假日基本走不动。<span class='src'>待验证的个例（只有 1 个来源）</span></li>
```

`.src` 用 `--ink3`，不跟打卡/避坑的色条抢——朱砂只留给「计划会失败」的那三类，
一个来源数是提醒，不是警报。

### 2. 那句话本身有个假话

界面里两处各写了一遍同一个三元表达式（行程页 `RouteRail.tsx`、城市页
`CityCandidates.tsx`）：

```ts
confidence === 'high'
  ? `${independent_source_count} 个独立来源`
  : '待验证的个例（只有 1 个来源）'
```

门槛是 `MIN_INDEPENDENT_SOURCES = 3`，所以**2 个来源的结论会被说成「只有 1 个
来源」**。那是在描述一个不存在的数字——而且因为它看起来只是保守，几乎不会被
注意到。（真库里那条「陕历博周一闭馆」当时正是 2 个来源，于是界面上写着
「只有 1 个来源」。它恰好是真的，纯属巧合；见第三节。）

收成 `domain.knowledge.describe_confidence` 一处，三档：

| 来源数 | 那句话 |
|---|---|
| ≥ 3 | `N 个独立来源` |
| 2 | `待验证的个例（2 个来源，未达交叉验证门槛）` |
| ≤ 1 | `待验证的个例（只有 1 个来源）` |

两个刻意的形状：

- **只收来源数，不另收一个置信度。** 级本来就是由数推出来的（`confidence_for`），
  两个入参就有传得不一致的可能，而那时界面会显示一个与数字矛盾的标签。
- **措辞在服务端出，前端只渲染。** `InsightOut` / `ClaimBriefOut` / 工作台的
  `ClaimOut` 都多一个 `confidence_text`；行程页与城市页那两段三元表达式删掉，
  命令行 `ls align show` 里自己判的「高置信 / 待验证个例」也删掉。跨语言的
  单一出处只能这么实现：Python 与 TypeScript 各写一份，就是两个可以各自跑偏
  的地方。

### 3. 真机数据现在长这样

```
ls export trip_5f8dec330aa1
《南京、西安 5 天》5 天、14 个天项、2 条预约
已写出 data\exports\trip_5f8dec330aa1.html（13 KB，零外部引用，可离线打开）
```

页面上的 21 条结论，每条后面都是「待验证的个例（只有 1 个来源）」。这是这份
数据的实情：5 篇素材、4 个独立来源、门槛 3，**没有一条结论被交叉验证过**。
不是回归，是终于说出来了。

## 三、过程中撞出来的两处，压在置信度的地基上

这两处都不在原计划里。发现它们的方式是同一个：**去看那个数字是怎么算出来的。**

### 1. 转载判重的长度粗筛漏掉了整类转载——设计列为致命的那条风险真的发生了

`ingest._find_repost` 里有一道粗筛：

```python
shorter, longer = sorted((len(existing), len(body)))
if shorter == 0 or shorter * 3 < longer:
    continue
```

理由是「长度差三倍以上时，较短的那篇被覆盖满也达不到阈值」。**这句话不成立**：
覆盖率的分母**就是较短的那一篇**（`similarity.overlap` 特意换过序，好让「长文里
摘了一段」与「把一段扩写成一篇」得到同样的判定），所以短篇被整篇照搬时覆盖率是
1.0，与两篇的长度差无关。

真库里的代价：

| | |
|---|---|
| 两篇素材 | 459 字《西安三天，博物馆和城墙》（知乎）、99 字《【转】西安博物馆预约提示》（携程） |
| 真覆盖率 | **0.722**（阈值 0.60，最长公共片段 44 字） |
| 粗筛 | `99 × 3 = 297 < 459` → 从没进过比对 |
| 后果 | 两篇都没归组；同一条「陕历博周一闭馆」算成「**2 个独立来源**」 |

设计第十一节的风险表第一行就是这件事：「独立来源去重失效 → 置信度退化成转发量，
整个信任模型是假的」。它在这份唯一真实的数据上发生了，而**全库唯一一条看起来
被交叉验证过的结论，其实是同一篇数了两遍**——那两篇里有一篇标题就叫「【转】…」。

改法与配套的三处：

1. **粗筛换成字符多重集合的交集占比。** 公共片段里的每个字符都必须同时出现在
   两篇里，所以「交集字符数 ÷ 较短篇长度」一定是真覆盖率的上界。O(n)，比
   `SequenceMatcher` 便宜，而且只会筛掉**确定**不够格的对。它故意是松的。
2. **补 `relink_reposts`：第一层原先只在导入那一刻跑。** 判据改过、或者导入时
   判错了，历史数据永远修不回来——而 ADR-0008 说得清清楚楚，归组是「可以对
   同一批素材反复执行的命令」。第二层做到了，第一层当时没有。配套加了
   `ls pipeline merge`（只重算置信度那一步），`ls group run` 现在两层都跑。
3. **`recount_independent_sources` 改成现查素材表**，不再读
   `claim_evidence.source_group_id`。那一列是**提纯那一刻**抄下来的快照，而归组
   按设计可以反复重跑；照快照算的话，ADR 要求的那个动作（「置信度一旦按文字复制
   口径算出高置信，第二层跑完之后是要被降级的」）永远不会发生。真库里 39 条证据行
   的组号**全是 NULL**，就是这么来的——只修判据、不修计数，数字一分都不会变。
4. **「数几个独立来源」原先有三份实现**（`domain/knowledge` 的属性、`save_claim`
   里的推导式、`recount` 里的 SQL），收成 `count_independent_sources` 一处。
   三份实现就是三个可以各自跑偏的地方，而它们都自称「独立来源数」。

顺带订正 `basis`：导入转载时建的组写的是 `domain_author`（同站同作者），判据明明
是 LCS 覆盖，该是 `similarity`。`schema.py` 里那句「`domain_author` 这个取值在
实现里没被用到」当时就是错的。

**修完之后的真库**：1 个来源组（`similarity`，知乎原文 + 携程的【转】），
38 条结论的来源数**全是 1**。原先那条 2 个来源的「陕历博周一闭馆」回到了 1。

### 2. 一处判断只留了一个数字，但它原先待在三个地方

见上面第 4 条。写在这里是因为它的形状值得记住：**同一个数在三处各算一遍，
不会报错，只会让三处慢慢不一致**。发现它的办法是把「这个数字是怎么来的」
从界面一路问回数据库——问到最后发现有三份答案。

## 四、记下来单独做的一件：同一件事被拆成好几条——**尚未做**

路书那一页现在把问题照出来了。真行程的 21 条结论里：

| 同一件事 | 几条 |
|---|---|
| 陕历博周一闭馆 | 2（「不要安排周一去」/「安排行程时要避开」） |
| 游5路（306路）会拉你去买玉 | 2 |
| 从西安北站坐 14 号线转 9 号线到兵马俑 | 2 |
| 陕历博要预约、提前 3 天、8 点放票 | 5 |

后果有两层：一是手机上同一句建议读五遍；二是**置信度被拆散了**——同一件事的
若干说法各自记着 1 个来源，谁也没到门槛，而合起来本来能看出「有两篇素材都提到
它」。

这属于设计 4.3 里那个**尚未落地**的「结论同源」第二层（第 168 行写着「第二层的
实现在 M3 尚未落地」）。判据是「同一主体 + 同一 facet + 同一极性 + 正文近似」，
`merge_claims` 现有的判据只做「抹掉空白与标点后完全相同」，够不着
（「十四号线」与「14 号线」、「要」与「需」、「提前三天」与「提前 3 天」）。

**它不塞进置信度呈现这一件里**，因为它改的是知识库而不是界面，而且 ADR-0008
明确说放宽的误差方向是把独立来源错并成一个、把高置信降级——那是另一个方向的
错误，要单独定阈值、单独验。

## 五、边界情况——**已做**

做法是**拿退化输入把所有接口打一遍**，而不是只看我猜得到的那几处：建一份
只建了骨架、一行天项都没有的行程（城市是真有的，日期放在 2027 年），把
详情、覆盖率、软经验、预约清单、日历、待补坐标、路书全取一遍，再把不存在的
行程、认不出的城市名、空城市表、0 天、非法日期各打一遍。

结果里**没有一个是「接口报错」**。接口全都规规矩矩返回 200 或 4xx，问题在于
其中三处给出的**是一个看起来正常的假答案**。

> **后记：第 1 条与第 4 条涉及的功能已经放弃。** 那两处修完之后上真机，
> 手机日历**一个事件都不认**；再按 RFC 5545 逐条核对，产物还有两处 MUST 违规
> （`DTSTAMP:20260913T202107` 与 VTIMEZONE 里的 `DTSTART:19700101T000000`
> 都缺 `Z`）。**决定不再修，把日历导出整个删掉**——一个「可能不生效的提醒」
> 比「明说没有提醒」更糟：用户会以为自己被兜住了。删掉的清单与代价记在
> 第六节。这两个小节保留，因为里面的教训与该功能无关：**一条测试靠另一个
> bug 才通过**，以及**只写进响应头的信息等于没写**。

### 1. 导出的 `.ics` 一直是坏的，而日历客户端对它静默不认

`build_calendar` 把整个时区块当成 `raw` 列表里的**一项**交给折行函数，可它
内部已经含 `\r\n`：

```python
raw: list[str] = [..., _VTIMEZONE]          # ← 九行当成一项
body = "\r\n".join(fold(line) for line in raw)
```

折行是按**逻辑行**做的，所以那九行被当成一个逻辑行，在累计第 75 字节处硬切。
真机产出的字节（`repr` 出来的，不是从控制台抄的）：

```
 7 [15] 'BEGIN:VTIMEZONE'
 8 [18] 'TZID:Asia/Shanghai'
 9 [14] 'BEGIN:STANDARD'
10 [22] 'DTSTART:19700101T00000'
11 [ 2] ' 0'
...
15 [12] 'END:STANDARD'
16 [ 7] 'END:VTI'
17 [ 7] ' MEZONE'
```

`DTSTART:19700101T000000` 与 `END:VTIMEZONE` 在产物里**都不存在**。而按这个
模块自己开头写的那句话：「错了客户端会静默不认（不报错，只是事件不出现，
这比报错更难查）」。**日历是设计 6.2 里唯一把预约提醒送到手机上的通道**，
所以这个错的表现是「提醒从来没到过」，而服务端一点异常都看不到。

修法两处：

- 时区块改成**一行一项**的元组，`raw.extend(...)`。
- **`fold()` 收到含换行的文本时抛 `ValueError`。** 折行按定义就是按逻辑行做的，
  整块传进来只能切错位置——这种事必须当场炸，不能「折出来看着也像那么回事」。
  这道守卫要是当初就有，这个错一行都写不出来。

**现有测试为什么没拦住：** `test_has_the_required_envelope` 的必需清单里有
`BEGIN:VTIMEZONE` 与 `TZID:Asia/Shanghai`，而它们都在切点**之前**；
`END:VTIMEZONE` 不在清单里。测试列的那几个字符串恰好都活了下来。

**还有一条测试是靠这个 bug 才通过的：** `test_release_without_time_becomes_an_all_day_event`
断言「全文里不含 `T000000`」（意思是全天事件不带时刻）——而全文里当时真的没有
这串，因为时区块的 `DTSTART:19700101T000000` 被切开成了 `…T00000` 与 `0`。
修好折行之后它立刻变红。**一条测试靠另一个 bug 才成立，是两处互相掩护的典型。**

### 2. 「知识库没覆盖的城市直接搜高德」这条路从来没工作过

设计 5.1：知识库尚未覆盖的城市仍可直接搜高德。那条路实际每次调用都是一个
`TypeError`：

```
"amap_error": "TypeError: search_pois() takes 1 positional argument but 2 were given"
```

`_live_search()` 把 `search_pois` **原样返回**，而 `amap_fallback` 按位置传
`(关键词, 城市)`；真适配器的城市是**关键字**参数。别处四处
（`booking_store`、`meal_coords`、`pipeline`、`realign`）都包了一层
`lambda keywords, city: search_pois(keywords, city=city)`，只有候选池这条漏了。

坏处被 `pool_for_city` 的宽 `except Exception` 接住，显示成
「高德补全没成功：TypeError…」——**把我们自己接错线说成了高德的失败**；而界面上
的表现只是少了几条候选加一句没人细看的小字，用户还以为「这城市没什么可去的」。

三处改动：

- `_live_search()` 返回包好的回调；`_live_fetch()` 加注说明它为什么不用包。
- `pool_for_city` **只接 `PoiSearchError`**（与 `pipeline._fetch_from_db`、
  `meal_coords` 同一条规矩）。高德挂了不该让整页报错，我们自己的接线错误必须炸。
- 城市页那句文案改成实话：「这座城市还没有攻略数据，去高德搜也没成功：…。
  所以下面没有候选——**这跟「这里没什么可去的」不是一回事**。」原先写的是
  「高德补全没成功…缺坐标的地方在地图上暂时不可用」，两处都不对：`amap_error`
  只在**回落搜索**失败时被设置（补全那条路目前没有调用方），而且那种时候下面
  一条候选都没有，不是「缺坐标的地方不可用」。

**测试为什么没拦住：** `tests/test_api_candidates.py` 里那个假搜索函数写成
`fake_search(keywords: str, city: str)`，两个参数都能按位置收——于是它在接错线
时**也照样通过**。把它改成与真适配器同形（城市是关键字）之后，这条走过整条
真实路径的测试立刻变成钉子：把 `_live_search` 改回旧写法，它会红。

### 3. 天气两个来源都没取到时，来源照样写着「高德」

`forecast_for_city` 最后那个分支返回 `source=WeatherSource.AMAP` 配一个空
`days`，而 `note` 写的是「高德也没有返回这个区间的预报」。界面于是显示
「来源 高德」加一片空白——读的人会以为高德查过了、那几天就是没数据。

改成 `source=None`（**没有数据就没有来源**，与库里其它「算不出」一致），
API 的 `source` / `source_label` 随之可空，前端没来源就不显示那一句。
枚举加一个 `NONE` 成员也可以，但「未取到」不是一种来源，那是范畴错误。

**测试为什么没拦住：** `test_both_sources_empty_yields_an_empty_forecast_with_a_note`
测了这个分支，**但没断言来源**。现在断言了，另外补了两条同类分支：
城市没有坐标且高德没数据、高德有数据但被 `_clip` 裁空。

### 4. 日历里少了一条，而界面一个字都没提

这一条是**准备真机验证时**撞出来的：起好服务、从局域网地址取那两个文件，顺手
把响应头打出来看，才看见

```
x-booking-skipped: 秦始皇兵马俑博物馆
事件数 1
```

这份行程的预约清单里有 **2 条**，日历里只有 **1 个事件**——兵马俑那条**算不出
放票日**，进不了日历。而「跳过了谁」只写在一个 HTTP 头里，界面上那个下载是
普通 `<a href>`（`api.ts` 里 `bookingCalendarUrl` 的注释写着「日历是唯一的推送
通道，所以直接给链接而不走 fetch」）——**浏览器下载文件时响应头没有人看得到**。
`ics.py` 自己的注释恰好写着这条规矩：「**跳过的要报出来**：静默少一条会让用户
以为那个景点不用预约——这恰恰是设计里最怕的失败模式。」命令行
（`ls booking ics`）与 `scripts/verify_ics.py` 都会打印，只有界面这条路把它丢了。

真机上的表现会是：清单 2 条、日历 1 个事件，中间少的那一条没人解释。

改法是把这份名单放到用户看得见的地方：

- `ics.split_schedulable(alerts)` 成为「哪些进得了日历」的**唯一判据**，
  `build_calendar` 与 `/booking` 接口共用。两处各算各的，正是这类不一致的成因。
- `TripBookingOut` 多一个 `calendar_skipped`，界面在下载链接下面说出来。
- **它是与 `pending_review` 并列的另一类缺席**，不是同一件事：`pending_review`
  是规则还没复核（去复核），`calendar_skipped` 是规则已复核但没写提前天数
  （去补那个数）。混在一起说会让人查错地方。
- 顺带订正命令行那句含糊的话。它原先写的是「要么规则里没写提前天数，**要么规则
  还没复核**（草案不对用户可见）」——后半句是错的：`alerts_for_trip` 只从**已复核**
  的规则生成清单，草案根本变不成 alert，到不了 `skipped` 里。
- 测试四条：已复核但没 `advance_days` 的会出现在 `calendar_skipped`；
  **清单条数 − 跳过条数 = 日历里的事件数**（界面说的与产物里的必须是同一件事）；
  两类缺席不互相冒充；都进得去时这个字段是空的。

**这些改动随后跟着功能一起删掉了**（见下一节）。留下的教训与该功能无关：
**只写进响应头的信息等于没写。** 这条信息在命令行里是打印出来的、在脚本体检里
是打印出来的，只因为界面上那个下载是普通 `<a href>`，它就到了不了用户眼前——
而同一份代码的注释里恰好写着「跳过了谁必须报出来」。**一个判断被实现在了
没有人看的地方，与没实现它是一回事。**

### 顺带记下的一个还没改的边界

`POST /api/trips` 即使城市**已经在本地 `city` 表里**，也要问一次高德的行政区划
接口——也就是离线或配额耗尽时建不了行程。（写本文时把配额跑成了
`CUQPS_HAS_EXCEEDED_THE_LIMIT`，才发现这件事；接口本身报得很诚实：502
`amap_unavailable` 加原始原因。）

改法很清楚：解析前先查本地表，命中就不联网（`candidate_pool.city_adcode_for`
已经是这么做的）。但它动的是「哪个来源算数」这件事，不是纯粹的边界修补，
所以留作单独一件。

.venv\Scripts\ls.exe export trip_5f8dec330aa1                        # 路书仍然要能导出

## 六、放弃日历导出——**已删**

设计 6.2 原本把「导出 `.ics` 交给手机系统日历」定为**唯一能把提醒送到用户手上
的通道**（本项目是本地工具，用户不会一直开着它，而预约的要害是时点）。它现在
被删掉了。

### 过程

| 步骤 | 结果 |
|---|---|
| 真机第一次导入 | 手机日历**一个事件都没有** |
| 查产物 | 折行把整个时区块当成一个逻辑行硬切，`DTSTART:19700101T000000` 与 `END:VTIMEZONE` 在产物里都不存在——**修了**（第五节第 1 条） |
| 再查 RFC 5545 的 MUST | 还有两处：`DTSTAMP` 与 VTIMEZONE 里的 `DTSTART` **都不是 UTC**（缺 `Z`）。补上是两个字符 |
| 决定 | **不再修，整个功能删掉** |

### 为什么两处 `Z` 就能修，还是删了

因为**这个功能的失败模式是静默的，而它要承担的是「别让我白跑一趟」**。
它已经失败过三次：折行切坏时区（客户端不报错、只是事件不出现）、跳过名单只写在
响应头里（界面一个字没提）、以及两处 UTC 违规。每一次都是同一类——
**产物看着完全正常，用户以为被兜住了，实际没有**。设计把「预约规则错误」列为
唯一会直接伤害用户的失败模式；一个"可能不生效的提醒"在这个位置上比"明说没有
提醒"更糟。

### 删掉了什么

| 层 | 内容 |
|---|---|
| 服务 | `lushu/services/ics.py`（整个模块） |
| 接口 | `GET /trips/{id}/booking.ics`、`TripBookingOut.calendar_skipped`、`X-Booking-Skipped` 头 |
| 命令 | `ls booking ics` |
| 脚本 | `scripts/verify_ics.py`（它自称核对的正是「别人解出来的东西对不对」，但只查了「VTIMEZONE 在不在」，没查那两条 UTC 的 MUST） |
| 测试 | `tests/test_ics.py` 整个文件；预约接口里两个类；空行程接口里三条 |
| 前端 | `bookingCalendarUrl`、`calendar_skipped`、预约面板上的下载按钮 |

### 代价（要写在明处）

**预约提醒现在没有推送通道**，只有打开这份行程才看得到。界面上那句话
从「导出日历之后，提醒会由手机系统负责」改成了「**提醒只在你打开这份行程时
看得到**——它不会主动找你，所以到了该抢票的那几天，记得回来一趟」。
设计 6.2 与 M4 的里程碑行、README 的功能清单都同步改了；
`docs/M4-STATUS.md` 保留原文但加了文首订正——它是 M4 当时的实况，
不改写历史，但不能让读的人以为那条还在。

一件**没有**随功能丢掉的东西：兵马俑那条「已复核但没写提前几天放票」，行程页的
预约清单里照样能看到（`headline` 说的是「官方未公布放票口径」，只是不再显示
放票日那一行）。所以信息没少，少的只是「自动提醒」。

## 七、性能——**已做**

原计划是「给 `candidate_pool._fill_ratings` 加个上限与节流」。真去看它为什么
存在之后，结论是**把它删掉**——它花掉的东西（每一次规划请求里最坏 60 次串行
高德请求、无节流、无上限）换不来排程上的任何差别。

### 它的理由消失了两遍

`_fill_ratings` 是 M5 加的，代码注释写着：

> 引擎的 `attraction_search_node` 拿到景点清单之后要过一道 `filter_by_rating`，
> **评分缺失一律视为不达标**。池子里的地方是我们已经认定「有人写过」的，
> 却会因为高德没给评分被那道门禁丢掉——夫子庙正是如此。

第一遍：**同一天的下一节就把这道门禁改了。** `c7bfeb4`（「池子条目豁免评分
门禁：连节点一起换」）让池子条目不受门禁管——门禁只作用在「高德补全」那一部分
（`engine/pool_search.py` 的 note 里写着「候选池 N 个（不受评分门禁管）」）。
门禁的意图是滤掉高德搜出来的噪声（停车场、售票处、上车点），拿它去滤已经认定
过的条目，本来就是判据用错了对象。

第二遍：**就算门禁还在，补的那个数也到不了引擎。** `to_spot` 优先用高德的原始
响应转换（那份 raw_json 是字段约定的权威），而高德对这类地方给的 `biz_ext.rating`
是**空列表**。实测：

| | 列里的 rating | `to_spot` 出来的 rating | 有原始响应 |
|---|---|---|---|
| `B0FFHOSW24` 夫子庙 | None | **None** | 是 |
| `B001D1388K` 洒金桥 | None | **None** | 是 |

所以补进 `poi.rating` **列**的那个值，在 `to_spot` 那里被丢掉。真库里 26 个
没评分的 POI 全都带原始响应，没有一个走「列拼出来的」那条兜底。

### 改了什么

- `pool_pois` 不再补评分，`fetch` 参数与 `_fill_ratings` 整个删掉。**排程这条路上
  一次网都不打**——库里的东西够它用。
- 补评分这件事留在它该在的地方：城市页的 `fill_gaps`（默认不开，界面首屏不该
  等一串网络请求）。
- 测试换成一条**钉子**：`test_pool_pois_never_calls_amap` 把 `fetch_poi` 与
  `search_pois` 都换成「一被调用就 AssertionError」，再跑 `pool_pois`。
  另外两条钉住缺评分的正确表现：如实带出去（不编数），以及没有评分的地方
  仍然能变成引擎要的 spot。
- `docs/M5-STATUS.md` 里那句「不补的话，池子里没评分的地方连进清单的资格都没有」
  加了订正——它在写下的当时是对的，同一天就被下一节推翻了。

### 数量

真库里池子条目 10 个（南京 5、西安 5），其中 2 个没评分 → 删掉之前每次规划
2 次串行请求。换成一座新城市的池子（`limit=60`）就是最坏 60 次。规划本来就要
等一次 LLM 调用，但多出来的这串请求没有任何一处能看出来。

### 真库上核对过

改动最该担心的后果是「没评分的地方进不了清单」。在真库上走了一遍节点在
「池子够用」那条路上的动作（`provider(城市)` → `to_spot` → 进清单）：

| 城市 | 池子 | 进清单 | 没评分的那个 |
|---|---|---|---|
| 南京 | 5 | **5 / 5** | 夫子庙 `B0FFHOSW24`（列里与 spot 都是 None） |
| 西安 | 5 | **5 / 5** | 洒金桥 `B001D1388K`（同上） |

两个池子都 ≥ `THIN_COVERAGE`（3），所以走的是封闭世界那一支；两个没评分的
地方都进了清单。**删掉那串请求，一个候选也没少。**
