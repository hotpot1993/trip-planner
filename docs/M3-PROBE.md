# M3 前置实测记录

M3 的三个致命风险都是「效果类」风险（见 docs/DESIGN.md 第十一节），
按 M2 的做法，动手前先拿真实调用把不确定的地方量出来。本文件只记录**实测结论**，
设计随之修正的地方会指向对应的文档改动。

探测脚本都在 `scripts/` 下，可以随时重跑。

## 一、提纯能不能做到「引文必须是原文子串」

脚本：`scripts/probe_m3_extract.py`

设计里写死了一条规则：凡是在原文里找不到对应片段的候选一律丢弃
（docs/DESIGN.md 4.2）。这条规则的前提是模型给出的引文确实是原文的连续子串，
之前没有验证过。

**结论：成立，而且是精确子串级别。**

| 项目 | 实测 |
|---|---|
| 结构化输出 | `with_structured_output(schema, method="function_calling", strict=True)` 可用 |
| 两篇素材（721 字 / 585 字） | 分别抽出 14 条与 15 条，合计 29 条 |
| 引文精确命中原文 | **29 / 29（100%）** |
| 引文需要「去空白去标点后」才命中 | 0 条 |
| 引文完全找不到 | 0 条 |
| 单篇耗时 | 4.2s / 4.5s |

模型的引文连原文里的换行、空格、直角引号都原样保留，所以校验不需要做
模糊匹配的兜底。**宽松匹配仍然要实现**，但定位为诊断用：真实网文里有全角
半角混排、错别字、平台插入的表情符号，一旦出现 `loose` 命中就说明该篇素材
的正文清洗不到位，属于要看的信号，不是要静默接受的常态。

### 1.1 落成适配器之后复验一次：17/17 精确命中

脚本：`scripts/verify_extract.py`（打真接口，结果进 llm_cache）

上面那轮探测是一次性的脚本；落到 `lushu/adapters/extract.py` 之后又跑了一遍
真实调用，确认提示词与结构化输出在正式代码里同样成立：

| 项目 | 结果 |
|---|---|
| 两篇素材（396 字 / 346 字） | 模型吐出 17 条，**引文校验通过 17、丢弃 0** |
| 精确子串命中 | **17 / 17（100%）**，宽松命中 0 |
| 单篇接口耗时 | 3.2s / 2.5s |
| 第二次调用 | 两篇都命中 `llm_cache`，总耗时 **0ms** |

### 1.2 `facet` 的标注不可靠，但影响有限

同一批结果逐条看，发现模型对 `facet` 的归类会前后矛盾：

| 结论 | 模型给的 facet | 更合适的 |
|---|---|---|
| 陕历博周一闭馆 | — | `closure` |
| 故宫需提前 7 天预约 | `other` | `hours` 或 `price_diff` |
| 城墙白天太晒 | `hours` | `crowd` 或 `other` |

**影响范围是可以界定的**：`facet` 在本项目里只决定两件事——
复验周期（`lushu/domain/knowledge.py` 的 `_REFRESH_DAYS`）与界面上的分组呈现。
它**不参与**接地校验（那是 `quote` 的事），也不参与置信度（那是独立来源数的事）。
所以标错一个 facet 的后果是「这条结论的复验提醒早来或晚来几个月」，
不会让一条假结论进入知识库。

当前的处理是：认不出来的 facet 归到 `other` 而不是丢掉结论
（`lushu/adapters/extract.py` 的 `_facet_or_other`）。**不做**提高 facet 准确率的
额外投入——金标准集跑起来之后才知道它值不值得修，现在调就是盲调。

同时观察到三件影响后续设计的事：

1. **一条引文可以支撑多条结论**。「城墙推荐傍晚上去…全程 13.7 公里」同时产出了
   「建议傍晚上」和「一圈 13.7 公里」两条，引文指向同一段原文。所以
   `claim_evidence` 与 `claim` 是**多对多**，不能按引文去重。
2. **主体粒度会漂移**。「东华门只能出不能进」的主体被抽成独立的「东华门」，
   而它其实是故宫的一个门。这类提及必须能对齐到具体实体，
   否则会生成一个只有一条结论的孤立 POI。
3. **不出错也不代表有用**。29 条里「不倒翁小姐姐那个表演现在好像已经没有了」
   这类内容被抽出来了，它确实是避坑信息，但它指向的不是一个地点。
   对齐阶段必须允许「对不上」这个结论，而不是硬塞一个近似结果。

## 二、独立来源归组：4-gram 与 SimHash 都不够，LCS 覆盖可用但有一档盲区

脚本：`scripts/probe_m3_grouping.py`

样本是一篇原文加四个变体：转载照搬、洗稿改写（每句都换说法）、转载节选、
同城异作者的同类攻略、异城异作者的无关攻略。同篇组合 3 对，异篇组合 7 对。

| 指标 | 同篇区间 | 异篇区间 | 判别力 |
|---|---|---|---|
| 字符 2-gram Jaccard | [0.140, 0.333] | [0.025, 0.079] | 1.8× |
| 字符 3-gram Jaccard | [0.067, 0.299] | [0.000, 0.033] | 2.0× |
| 字符 4-gram Jaccard | [0.045, 0.278] | [0.000, 0.012] | 3.7× |
| **LCS 覆盖（≥12 字连续片段）** | **[0.051, 0.852]** | **[0.000, 0.000]** | **完全分离** |
| SimHash 海明距离 | [27, 34] | [26, 34] | **区间重叠，无判别力** |

三条结论：

1. **SimHash 在这件事上没有用。** 同篇与异篇的海明距离区间完全重叠
   （同篇 27–34，异篇 26–34）。SimHash 的降维前提是长文本里随机差异会相互
   抵消，而中文攻略常见长度只有几百字，这个前提不成立。
   `source_document.simhash` 这一列**保留但不用作判据**，只留作调试信息。
   这一点和 M2 的 12306 价格接口是同一类教训：先探测再动手。

2. **Jaccard 的分离度随 n 增大而变好，但绝对水平很低。** 最优的 4-gram 下
   同篇最低只有 0.045，而阈值扫描显示任何 ≥0.2 的阈值都抓不到
   「洗稿改写」那一对。所以 Jaccard 不能单独作判据。

3. **LCS 覆盖是唯一能把异篇压到 0 的指标**，用的是
   `difflib.SequenceMatcher` 找出所有 ≥12 字的公共连续片段，
   看短的那一篇被覆盖了多少比例。

### 盲区：完全改写认不出来

LCS 覆盖里「转载照搬」0.852、「转载节选」0.852，而「洗稿改写」只有 0.051 ——
**和异篇的 0.000 一样低**。这不是阈值没调好：那一篇每一句都换了说法
（「晚上8点不是零点」→「晚上八点不是零点」），已经不存在 ≥12 字的公共片段。

这暴露了设计里没说清的一件事：**「独立来源」到底按什么算**。

- 若按**文字复制**算，改写过的转载就是一个新来源，置信度会虚高。
- 若按**结论同源**算，就该在两篇的提纯结果上比对，而不是在正文上比对。

设计原文（4.3）说的是「归组依据是域名、作者与正文相似度三重判断」，
按实测这个说法在改写面前是漏的。正确的两层结构是：

| 层 | 判据 | 抓什么 | 现状 |
|---|---|---|---|
| 第一层 文字复制 | LCS 覆盖 ≥ 阈值 | 照搬、节选、换标题重发 | 本次实测可行 |
| 第二层 结论同源 | 两篇提纯出的结论高度重合 | 逐句改写的洗稿 | **尚未实现，见下方待办** |

第二层必须在提纯之后才能做，所以归组不能是「导入之后一次算完」的动作，
而是一个可以**在提纯完成后重跑**的步骤。这一点会改变管线形状：
导入时先按第一层给出暂定分组，提纯之后再按第二层修订。

第二层的阈值不能照抄第一层。两位真的各写各的游客，写同一座城市的同一批
景点，结论天然会有重合（「故宫要提前预约」人人都写）。所以第二层必须要求
**高度重合**（例如一篇的结论有 ≥80% 能在另一篇里找到同义项），
否则会把独立来源错并成一个，把高置信结论降级——这是保守方向的错误，
但同样是错误。

## 三、实体对齐：`parent` 字段可用，`adcode` 作 city 参数会把结果筛没

脚本：`scripts/probe_m3_align.py`、`scripts/probe_m3_poi_fields.py`、
`scripts/probe_m3_poi_parent.py`

### 3.1 高德 POI 的层级靠 `parent` 字段，可以认亲

`/v3/place/text` 的返回里有一个之前没注意的字段：

| POI | id | parent |
|---|---|---|
| 故宫博物院 | B000A8UIN8 | （空） |
| 故宫博物院-午门 | B000A84GDN | B000A8UIN8 |
| 故宫博物院检票处 | B0FFKL520U | B000A8UIN8 |
| 陕西历史博物馆 | B001D03PEX | （空） |
| 陕西历史博物馆停车场 | B0FFHSIN65 | B001D03PEX |
| 秦始皇帝陵博物院 | B001D09OYW | （空） |
| 秦始皇兵马俑博物馆 | B0FFGXMLTU | B001D09OYW |
| 秦始皇兵马俑博物馆第1停车场 | B001D0095C | B0FFGXMLTU（不是顶层） |

所以「景点本体」与「本体内部的一个点」是可以从字段上分开的：
**`parent` 为空的是本体，非空的是子点**。不需要靠名称里有没有 `-` 这种
脆弱启发式——`陕西历史博物馆停车场`、`故宫博物院检票处` 的名称里都没有
连接符，但它们同样是子点。

层级可以不止一层：`秦始皇兵马俑博物馆第1停车场` 的直接父级是
`秦始皇兵马俑博物馆`，而后者的父级才是 `秦始皇帝陵博物院`。
按「走到根」的规则，这三个的**本体都是 `秦始皇帝陵博物院`**——
停车场与展厅不是独立的游览对象，行程里的一个天项就是这座博物院。
归并要沿 `parent` 链一直走到空为止。

这条直接决定了结论挂在哪一层：

- 搜「故宫」时，`故宫博物院` 是答案，带 `parent` 的一律不进候选。
- 搜「午门」时，`故宫博物院-午门` 是正确答案，但它 `parent` 指向故宫博物院。
  结论仍应挂到**故宫博物院**上——行程里的一天项就是故宫博物院，
  挂到午门会出现一个只有一条结论、无法参与路线排序的孤立 POI。
  原文说的「午门」通过证据引文保留，不丢失。

### 3.2 `city` 参数传 adcode 会把结果筛成 0 或筛错

同一段代码，`city` 传行政区划代码与传城市名的结果完全不同：

| city 参数 | 搜「故宫」 | 搜「钟楼」（西安） |
|---|---|---|
| `110100`（北京 adcode） | 返回 2 条，**全部是廊坊的故宫文创店** | —— |
| `610100`（西安 adcode） | —— | 5 条，正常 |
| `北京` / `西安`（城市名） | 10 条，`故宫博物院` 居首 | 5 条，`西安钟楼` 居首 |

传 adcode 时高德按「行政区内」而不是「城市内」理解，北京 adcode 命中的
是廊坊广阳区（`131003`）——因为大兴机场在行政上属河北。这是一个**静默错误**：
返回 200、有结果、字段齐全，只有 adcode 不对。

管线里 `city` 参数一律传**城市名**，取到结果后再用 `adcode` 前四位校验
是否落在目标城市内。两者分工不同，不能混用。

### 3.3 名称匹配的准确率取决于提及类型

20 条真实攻略里会出现的提及（北京 10 条、西安 10 条），
期望结果全部人工核对过：

| 提及类型 | 例子 | 表现 |
|---|---|---|
| 全称 | 故宫博物院、陕西历史博物馆 | 首位命中 |
| 俗称简称 | 陕历博、兵马俑 | 首位命中（高德有别名能力） |
| 带城市前缀 | 西安城墙、西安钟楼 | 首位命中 |
| 通用地标 | 角楼、钟楼、回民街 | 首位命中，但**返回的是子点或非景点类型** |
| 行政区/街区 | 洒金桥、金鱼胡同 | 首位是「道路名」「桥」这类地名，不是景点 |

原始首位命中 16/17 可判定条目，但这个数字**不能直接当作对齐准确率**，
因为「命中」只比对了名称，没有校验类型。逐条看会发现：

- 搜「角楼」，首位是 `故宫博物院-东北角楼`（正确，但它是个子点）。
- 搜「袁家村」在西安，前五**全是西安市区的中餐馆**，真正的袁家村在咸阳。
  名称完全一致，城市完全错误——这是最危险的一类错误。
- 搜「洒金桥」「金鱼胡同」，首位是 `地名地址信息;交通地名` 类型的道路名或桥名。

所以对齐的判据必须是**名称 + 城市 + 类型**三者，而且类型要分两类分别处理：
「值得去的地方」和「只是个地名」。只比名称的准确率是虚高的。

### 3.4 补齐祖先链之后，对齐在本批样本上 14/14

脚本：`scripts/verify_align.py`（打真接口）

3.1 节那条规则有个前置条件容易被忽略：**判断「本体还是子点」需要知道父节点
是谁，而父节点经常不在搜索结果里**。第一次跑验证脚本时对齐准确率只有 **14%**，
失败原因几乎全在这里——

| 症状 | 真实数据 |
|---|---|
| 本体在候选里但排在最后，子点被当成独立实体 | 搜「兵马俑」，十条结果里六条属于同一个本体，`秦始皇帝陵博物院` 排在最后一条 |
| 本体完全不在结果里 | 搜「午门」，`故宫博物院` **根本没返回**，只有 `故宫博物院-午门` |
| 同一批里并列 | 十个候选全部被判为「本体」，于是「前两名咬得紧就交人工」这条规则反复触发 |

修法是把候选集之外的祖先**查回来**：沿 `parent` 往上走，遇到本地没有的就查一次
`/v3/place/detail`，直到走到根（`lushu/adapters/poi_lineage.py`）。
一次验证共补查 24 个祖先节点，每个只查一次。

补完之后逐项修正，每一处都对应一个实测：

| 修正 | 触发它的实测 |
|---|---|
| 排序分不再夹到 1.0 | 夹了上界之后「完全相同」与「被包含」都是 1.0，差值恒为 0 |
| 「完全相同 / 在分隔符后完整出现」加成 0.20，「只是被包含」加成 0.12 | 搜「钟楼」，`钟楼` 与 `大慈恩寺-钟楼` 只差 0.10；搜「珍宝馆」，`故宫博物院-珍宝馆` 与 `国学艺术珍宝馆` 差 0.08 |
| 存在完全同名候选时，把「只是被包含」的再降 0.12 | 同上两例，降权后都能干脆选出答案 |
| 短词的整体包含不算信号 | 「西安」出现在几百个候选名里 |
| 「兵马俑」这类俗称只能靠包含关系或高德排序 | `兵马俑` 对 `秦始皇帝陵博物院` 的 SequenceMatcher 比例是 **0.00** |

**最终结果**（16 条样本，期望值逐条人工核对过）：

| 项目 | 结果 |
|---|---|
| 应当对齐的 14 条 | **命中 14** |
| 本来对不上的 2 条（「不倒翁小姐姐」「大唐遗宝展」） | **正确拒绝 2，错误接受 0** |
| 候选字段填充率 | `typecode` 100%、`parent` 62%、`rating` 64%、`open_time` 68% |

其中「午门」「神武门」「太和殿」「珍宝馆」「兵马俑」五条走的是**归并**路径
（命中子点 → 结论挂到本体），这正是 ADR-0009 想验证的行为。

**样本量的诚实说明**：16 条样本足以把上面那几类**结构性**错误暴露出来
（每一类都出现在多条样本上，不是孤例），但不足以给出一个可信的准确率数字。
设计里要求的 30 篇素材金标准集才是那个数字的来源。
`typecode` 100% 与 `raw_json` 100% 是结构性的，可以直接采信。

还有一条边界：`city` 参数的坑（3.2 节）与 `parent` 层级（3.1 节）
在验证脚本里都是**手工传对**的，正式管线里这两件事由服务层负责，
它们的正确性要靠服务层自己的测试守，不能靠这个脚本。

### 3.5 端到端跑真实数据后又发现两类错

脚本：`scripts/verify_pipeline.py`（5 篇素材，真实模型 + 真实高德）

| 现象 | 根因 | 处置 |
|---|---|---|
| 两篇素材提纯直接失败：`Unknown tool type: '\_ExtractionOut'` | 结构化输出的 `function_calling` 把**类名当工具名**发给服务端，而工具名要匹配 `^[a-zA-Z0-9_-]{1,64}$`。类名 `_ExtractionOut` 的下划线被服务端转义，于是对不上 | 类名改为 `ExtractionOut`。**假客户端测不出这类失败**，只有真实调用才会暴露 |
| 「洒金桥」因为「前两名得分相差 0.00」进待人工 | 高德对同一个地方有**三条同名记录**：`交通地名;桥`、`交通地名;立交桥`、`热点地名`，坐标在三百多米内 | `_merge_same_name_neighbours`：同名 + 同类 + 相距 ≤400 米视为同一个地方 |
| 「城墙」因为 0.61 < 0.80 进待人工 | 素材里说的「城墙」就是 `西安城墙`，名称得分只有 0.61（一个是二字词，一个是四字词） | **未修**。放宽会波及别的提及，要等金标准集给依据 |
| 「东华门」在前五名里没有对应的景点 | 高德搜「东华门」返回的是「东华门大街」「东华门路」这些道路名，门本身不在返回里 | **正确行为**。判为待人工而不是挂到一条街上 |

最后一类值得单独说：`故宫博物院-午门` 与 `故宫博物院-神武门` 两条都被
正确归并到了「故宫博物院」，实测 9 条对齐里有 3 条走的是归并路径——
ADR-0009 的核心行为在真实数据上成立。

## 四、第二层归组在真实数据上基本失效（负面结论）

脚本：`scripts/verify_pipeline.py` 与一次专项诊断

ADR-0008 定的两层结构里，第二层是「结论同源」：两篇提纯出的结论高度重合
就算同一来源。在真实数据上跑，**这一层没起作用，而且原因不是阈值**。

西安原文与它的逐句改写，9 条结论与 7 条结论，**精确指纹交集为 0**：

| 原文抽出的结论 | 洗稿抽出的结论 |
|---|---|
| 兵马俑门票 120 块需提前在官网或公众号买现场不卖票 | 兵马俑门票一百二要在官网或公众号上买现场买不到 |
| 从西安北站坐地铁 14 号线转 9 号线到达全程一个半小时 | 从西安北站坐十四号线换九号线可到兵马俑路上约一个半小时 |
| 陕历博免费但必须预约需提前 3 天在官方公众号预约每天早上 8 点放票 | 陕历博免费但必须预约官方公众号提前三天放票每天早上八点开抢 |

**提纯阶段的归一化把数字改写了**（120→一百二、14→十四、3→三、8→八），
所以结论正文层面的任何字面比较都会失效。换成更松的指标也救不回来：
用字符 2-gram Jaccard（阈值 0.45）重算两两覆盖率，结果是

| 组合 | 同源？ | 覆盖率 |
|---|---|---|
| 西安原文 ↔ 西安洗稿 | **是** | **0.00** |
| 西安原文 ↔ 西安节选转载 | 是 | 0.50 |
| 其余 8 对异源组合 | 否 | 0.00 |

也就是说：**「节选转载」量得出来（0.50），「逐句改写」量不出来（0.00）**，
而后者恰恰是第二层存在的理由。

### 这件事意味着什么

设计原文（4.3）说「中文旅游攻略的转载与洗稿极其普遍」。实测把这两者分开了：

- **转载**（照搬、节选）——第一层的 LCS 覆盖能认，ADR-0008 的实测数字成立
- **洗稿**（逐句改写、数字换中文）——两层都认不出，第二层的判据假设不成立

追根究底，**「独立来源」这个概念在洗稿面前没有字面判据**。
两篇文字完全不同、事实点全部重合的攻略，究竟是「同一篇被洗了」还是
「两个人去了同一批地方」，只有人看得出来。这与设计里那条自我警告是同一件事：

> 两位真的各写各的游客，写同一座城市的同一批景点，结论天然会有重合
> （「故宫要提前预约」人人都写）

### 当前的处理

第二层保留在管线里（`group_by_conclusions`），因为它对**轻度改写**是对的
（节选转载量到 0.50），而且它有 `MIN_CONCLUSIONS_TO_COMPARE = 4` 的下限保护。
但**不要把它当成能兜住洗稿的东西**。

要真正解决，需要的是标注数据而不是更聪明的字符串比较：

1. 金标准集里带上「这几篇是不是同源」的人工标注
2. 实测「主体集合重合度」这个信号——两篇写同一座城市的**同一批 POI**
   比两篇写同一座城市的一般攻略更像同源。但这个信号也可能误伤
   「两位游客去了同一批必去景点」，**必须用标注数据量过才敢用**
3. 在拿到数据之前，宁可让置信度偶有虚高（多算一个来源），
   也不要错并（把两个独立来源算成一个、把高置信结论降级）——
   两者都是错，但方向不同，见 ADR-0008

## 五、顺带发现：现有 poi 表的 `typecode` 与 `raw_json` 是空的

脚本：`scripts/probe_m3_poi_parent.py` 第三节

M2 落库的 14 条 POI 里：

| 字段 | 现状 | 应该来自 |
|---|---|---|
| `rating` | 有值（4.5–4.7） | `biz_ext.rating` |
| `open_time` | 有值（`08:30-17:00`、`全天开放`） | `biz_ext.opentime2` |
| `typecode` | **全部为 NULL** | POI 顶层 `typecode` |
| `raw_json` | **全部为空** | 高德返回的完整 POI |
| `address` / `tel` | 部分有 | 顶层 `address` / `tel` |

`rating` 与 `open_time` 的取值路径在引擎里是对的
（`third_party/floattrip/providers/amap/poi.py` 的 `poi_to_spot` 读的是 `biz_ext`），
所以这两个值是真从高德来的，不是编的。**空的只有 `typecode` 与 `raw_json`。**

但这两个空字段正好卡住 M3：

1. 没有 `typecode` 就没法把「停车场」「公交站」「公厕」从候选里分出去，
   也没法区分「值得去的地方」与「只是个地名」。
2. 没有 `parent` 就没法实施上一节的层级归并。

原因是：引擎的 `poi_to_spot()` 只保留它规划要用的字段，原始 POI 在到达
`final_plan` 之前就被丢掉了，所以行程落库时无从补写 `raw_json`。

**结论：M3 需要一个自有的高德 POI 适配器**（`lushu/adapters/poi.py`），
直接用 `extensions=all` 查 `/v3/place/text`，把完整响应留下来。
它同时承担三件事：对齐时搜候选、补齐 poi 表的空字段、给候选池预热。
不需要为此改引擎——引擎的 `poi_to_spot` 保持原样（它是第三方代码，
改动越少越好），我们走自己的适配器。
