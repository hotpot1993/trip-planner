# 路书 · 设计文档

本文档记录「路书」的设计共识。术语以 `CONTEXT.md` 为准，关键决策的理由以 `docs/adr/` 为准，本文不再重复理由。

- 定位：自用与小圈子的本地旅行攻略工具，不做账号体系、不做部署、不做合规运营
- 覆盖：中国大陆优先，首批北京、西安、成都、上海
- 与参考项目的关系：全新项目；从 FloatTrip 隔离拷贝可复用模块（ADR-0005）；travel-plan-viz 只借鉴思路、不拷代码（第八节）

---

## 一、项目要解决的三个问题

1. **网友攻略里的信息不可信也不可用**——它们是散落的自然语言，且充满过时、转载与个例。要把它们变成可溯源、有置信度、能挂到具体景点上的结论。
2. **需要预约的景点会让用户白跑一趟**——故宫、陕西历史博物馆这类景点的预约规则（提前几天、几点放票、哪个渠道）必须准确且醒目。
3. **一次旅行常常跨多座城市**——而市面上大多数工具默认单城市。城际移动的交通方式、费用、停留天数分配全是空白。

其中第 3 项是产品的骨架：用户直接操作的界面与数据结构都以它为中心，第 1、2 项是往这个骨架上挂的信息层。

## 二、总体架构

```
浏览器（Vite + React + TypeScript + Tailwind + shadcn/ui）
    │  HTTP / SSE
    ▼
FastAPI 应用服务（本地 localhost）
    ├── 行程服务      城市停留 / 天 / 城际转移 / 排程触发 / 差异确认
    ├── 预约服务      预约规则 / 预约清单 / 日历导出
    ├── 知识服务      结论 / 证据 / 置信度 / 候选池
    ├── 运行服务      Run 持久化 / 事件流 / 对话
    └── 工作台服务    待对齐 / 待复核 / 待标注
    │
    ├──────────────┬──────────────────┐
    ▼              ▼                  ▼
Agent 编排      数据管线（CLI）      实体适配器
(LangGraph)     采集→提纯→去重        高德 POI / 高德天气
排程 / 对话     →对齐→入库→评测      Open-Meteo / 12306
    │              │                  │
    └──────────────┴──────────────────┘
                   ▼
         SQLite（WAL）
```

**依赖方向固定为：接口层 → 应用服务 → 领域逻辑 → 适配器 → 存储。** 反向依赖一律视为缺陷，并用测试守护（这一条沿用 FloatTrip 的 `test_architecture_boundaries.py` 思路）。领域层不允许导入 Web 框架、响应对象或前端协议。

**数据管线必须与 Web 进程分离。** 采集、提纯、对齐、评测都是长任务，做成独立 CLI 子命令，不占用 Web 进程，也不因为浏览器关掉而中断。

## 三、数据模型

### 实体域（硬事实，来自高德）

| 表 | 关键字段 |
|---|---|
| `city` | `adcode`、名称、`lat_gcj02`、`lng_gcj02` |
| `poi` | `amap_poi_id`（主键）、名称、`city_adcode`、`adcode`、地址、`lat_gcj02`、`lng_gcj02`、电话、类型、原始响应、抓取时间 |

`amap_poi_id` 是整个系统的实体主键（ADR-0002）。坐标字段名显式带坐标系后缀（ADR-0003）。

### 素材域

| 表 | 关键字段 |
|---|---|
| `source_document` | 站点、原链接、作者、标题、正文全文、正文指纹、`source_group_id`、导入时间、发布时间 |
| `source_group` | 独立来源归组：归组依据（域名加作者、或正文相似度）、代表素材 |

攻略素材全文长期留存为本地底档，且只留在本地（Q46）。**置信度按 `source_group` 计数，不按 `source_document` 计数**——这是整个信任模型的闸门（Q34）。

### 知识域

```
claim  结论
  subject_type   poi | route | city
  subject        poi_id | (poi_a_id, poi_b_id) | city_adcode
  polarity       avoid（避坑） | highlight（打卡）
  facet          排队 | 入口 | 时段 | 人流 | 拍照 | 交通 | 票价差异 | 闭馆 | 其它
  text           归一后的陈述
  confidence     high | single_source
  first_seen_at / last_verified_at / verify_due_at / status

claim_evidence  证据：claim_id、source_document_id、原文片段、字符偏移、source_group_id
alignment_task  待对齐：提及名、城市、上下文片段、候选 POI、状态、最终 poi_id
```

三层结论（景点级、路线级、城市级）共用同一张 `claim` 表，区别只在 `subject_type` 与 `subject`（ADR 未单列，理由：不会使模型变复杂）。

### 预约域

```
booking_rule  预约规则
  poi_id、booking_required
  advance_days        需提前几天
  release_time        放票时点（如「提前 7 天 08:00」）
  channels            渠道列表：名称、链接、类型（网页 | 小程序 | 公众号 | 电话）
  requires_real_name  是否实名
  closed_days         闭馆日（星期几或日期区间）
  status              draft（草案）| reviewed（已复核）
  reviewed_at / reviewer_note / verify_due_at / evidence_url
```

`status = draft` 的规则不得展示给用户（Q10）。

### 行程域

```
trip                行程：名称、出发日期、状态
city_stay           城市停留：trip_id、city_adcode、顺序、stay_days（停留天数）
day                 天：trip_id、city_stay_id、日期、在该城市内的序号
day_item            天项：day_id、顺序、类型（景点 | 餐饮 | 休息）、poi_id、起止时间、来源（AI | 手动）
intercity_transfer  城际转移：from/to 城市停留、归属 day_id、交通方式、车次/航班、起止时间、
                    耗时、票价、价格来源、交通方式建议理由、备选方案
leg_option          同城相邻点移动方案：起终天项、方案列表（方式 / 耗时 / 费用 / 是否首选 / 导航深链）
budget_item         预算项：类别（城际交通 | 市内交通 | 住宿 | 餐饮 | 门票 | 其它）、
                    金额、是否参考价、来源
```

关键形状：**行程 → 城市停留[] → 天[]**（ADR-0004）。`stay_days` 是用户输入，总行程天数是各 `stay_days` 之和，不由天数列表反推。

`intercity_transfer` 必须挂在某一天上，且该天归属于某一个城市停留——归属规则默认出发城市停留的最后一天，按实际车程自适应，用户可拖拽覆盖（Q45）。

### 运行与对话域

从 FloatTrip 拷贝并沿用的部分：`conversation`、`message`、`run`、`run_event`、`memory_fact`，以及事件溯源式的事件序号与断线回放机制。

**必须扩展的部分**：`planning_brief` 原本是单目的地结构，需要容纳城市停留序列。这是多城市骨架的真正改动点——不在界面里，在对话的数据契约里（Q38）。

### 人工介入域

```
workbench_task  数据工作台任务：类型（align | review_booking | gold_label）、
                关联对象、状态、载荷、创建时间、处理时间、备注
gold_set        金标准集：素材 + 人工标注的全部真实结论
```

三类任务共用一个工作台页面，交互形状相同（Q47）。

## 四、数据链路

### 4.1 采集与导入

两种入口（Q29）：粘贴正文（单篇精读）、导入 HTML 或 Markdown 文件（批量囤稿）。数据源优先级：马蜂窝游记、知乎问答、穷游与携程攻略、小红书公开页；不碰任何需要登录的内容（Q9、Q22）。

导入即计算正文指纹，为后续相似度去重做准备。

### 4.2 提纯

对每篇素材调用廉价的批量模型，抽取结构化结论候选，每条候选必须携带原文片段与字符偏移作为证据。**提纯只做搬运与归一，不产生新事实**——凡是在原文里找不到对应片段的候选一律丢弃。

产出不是结论，而是「待验证的经验」。

### 4.3 独立来源归组

这是必须先于置信度计算的一步，也是很容易被跳过的一步（Q34）：中文旅游攻略的转载与洗稿极其普遍，一篇爆款会被同步到十几个站点。**不做这一步，所有置信度分级都是假的**——置信度会退化成转发量。

归组是两层结构，不是「域名、作者与正文相似度三重判断」一次算完的动作（ADR-0008）：

| 层 | 判据 | 抓什么 |
|---|---|---|
| 第一层 文字复制 | LCS 覆盖（`difflib.SequenceMatcher` 找出所有 ≥12 字的公共连续片段，算较短一篇被覆盖的比例） | 转载照搬、转载节选、换标题重发 |
| 第二层 结论同源 | 两篇提纯出的结论重合度 | 逐句改写的洗稿 |

第一层用 LCS 覆盖，因为它是实测里唯一能把异篇压到 0 的指标：同篇 [0.051, 0.852]，异篇 [0.000, 0.000]。字符 4-gram Jaccard 的同篇区间是 [0.045, 0.278]、异篇 [0.000, 0.012]，判别力 3.7×（2-gram 与 3-gram 更差，只有 1.8× 与 2.0×），但任何 ≥0.2 的阈值都抓不到「逐句改写」那一对。SimHash 的海明距离同篇 [27, 34]、异篇 [26, 34]，**区间完全重叠，无判别力**——它的降维前提是长文本里随机差异相互抵消，而中文攻略常见只有几百字，前提不成立；`source_document.simhash` 保留但只作调试信息，不作判据。

**盲区**：LCS 覆盖认不出「逐句改写」——那一篇实测 0.051，与异篇的 0.000 一样低。所以需要有第二层，它比对的是两篇的提纯产物而不是正文。第二层的阈值必须比第一层**严**：两位真的各写各的游客写同一座城市的同一批景点，结论天然会重合（「故宫要提前预约」人人都写），因此要求一篇的结论有 **≥80%** 能在另一篇里找到同义项，才算结论同源。阈值放宽的误差方向是保守的（把独立来源错并成一个、把高置信结论降级），但同样是错误。第二层的实现在 M3 尚未落地。

因为第二层跑在提纯产物上，**归组不是导入之后一次算完的动作，而是可以在提纯完成后重跑的步骤**：导入时先按第一层给出暂定分组，提纯之后再按第二层修订。

### 4.4 实体对齐

提纯阶段产出的是自然语言景点名加上下文线索（城市、行政区、同行景点）。对齐阶段用高德搜索，取到 `amap_poi_id`；对不上的进入待对齐队列，由数据工作台人工处置（Q19）。

对齐的判据是**名称 + 城市 + 类型**三者，缺一不可，理由是实测里三者各自都会静默出错：

- **城市**：`city` 参数传 adcode 会把结果筛错。搜「故宫」传 `110100`（北京 adcode）只返回 2 条，**全部是廊坊的故宫文创店**；传城市名「北京」返回 10 条且 `故宫博物院` 居首。传 adcode 时高德按「行政区内」而不是「城市内」理解，北京 adcode 命中的是廊坊广阳区（`131003`）——因为大兴机场在行政上属河北。这是一个返回 200、有结果、字段齐全的静默错误。管线里 `city` 一律传**城市名**，取到结果后再用 `adcode` 前四位校验是否落在目标城市内。
- **只比名称的准确率是虚高的**：搜「袁家村」在西安，前五**全是西安市区的中餐馆**，真正的袁家村在咸阳。名称完全一致，城市完全错误，这是最危险的一类错误。
- **类型分两类处理**：「值得去的地方」与「只是个地名」。搜「洒金桥」「金鱼胡同」，首位返回的是 `地名地址信息;交通地名` 类型的道路名或桥名，不是景点。类型判据依赖 `typecode`，而现有 `poi` 表的 `typecode` 全部为 NULL，补齐它是 M3 自有 POI 适配器的职责之一。

层级靠 `parent` 归并到本体（ADR-0009）：`parent` 为空的才是本体，搜「故宫」要排除带 `parent` 的候选（`故宫博物院-午门`、`故宫博物院检票处` 等 9 条），搜「午门」时返回的正是子点，要沿 `parent` 链归并到 `故宫博物院`。归并结果显式记录「提及名」与「归并到的本体」两个字段，原文里说的子点通过证据引文保留。

坐标、地址、开放时间等硬事实全部随 POI 一起从高德获取，攻略素材对这类字段只能标注差异、不能覆盖（ADR-0001）。

### 4.5 入库与置信度

一条结论只有在同时满足三件事时才能进入攻略知识库：有原文证据、已对齐到 POI（或城市/路线主体）、独立来源数已计入。置信度由独立来源数决定，多源的为高置信，单源的标为待验证个例。

### 4.6 复验

按结论类型设定不同周期（Q49）：预约规则与门票开放时间 90 天、交通方式与人流高峰等易变经验 180 天、景点本身的存在与位置不设期限。到期后状态变为待复验，**在界面上标注而不隐藏**——过期的经验仍有参考价值，但用户必须知道自己正在看旧信息。

**到期是个静默事件**：日期一天天过去，库里那行数据一个字都没变。所以它不能只靠人记得，得有一条命令去问：`ls verify scan` 报出已过期与快到期（默认提前 14 天）的两类东西，`--apply` 才把过期的结论标成待复验，默认只报不改。已经到期的预约规则也报，但**不改状态**——把规则打回草案，用户那边的提醒就消失了，他会以为「这个景点不用预约」，那正是本项目最怕的失败模式。

周期只在两处定义：规则在 `domain/booking.py`（复核日加 90 天），结论在 `domain/knowledge.py`（按 `facet` 分档）。`services/verify.py` 一行周期常量都没有，只读算好的日期——否则同一个「90 天」会有两个出处，分岔的表现是「界面上还新鲜、命令行说已经过期」。代价是**将来实现「复验通过」时必须同时刷新 `claim.verify_due_at` 列**（该列会因此失效，届时改成实时计算）。

### 4.7 金标准集与评测

提纯质量「无金标准集就无法判断」是设计里点名的风险：只看抽出来的那些条，永远分不清「提纯很准」与「只看到了准的那几条」。所以 M3 的完成标志不是「链路能跑」，而是**能报出三个数字**。

金标准集是人工读原文写下的全部真实结论，标注必须落回原文（引文要能在正文里定位，位置由服务端算）。一篇读完发现全是废话的素材，**零标注行也是重要的标注结果**——它进召回率的分母，所以「标完了」是一个显式记录（`gold_set` 表），不能靠有没有标注行反推。

命中判定按「主体 + 极性 + 事实点位置」三关，不按文本相似度——理由与完整取舍见 ADR-0010。三个指标的口径：

| 指标 | 分子 / 分母 | 说明 |
|---|---|---|
| 抽取召回率 | 命中的条数 / 人工标注的全部条数 | 漏了哪些，一并列出原文片段 |
| 抽取精确率 | 命中的条数 / 模型抽出的条数 | 多抽的每一条都带「差在哪一关」 |
| 对齐准确率 | 挂对的条数 / 判得出来的条数 | 挂错与压根没挂上都算错，但分开报数 |

**样本量必须与指标并排出现。** 设计要的是 30 篇素材的标注集；不到这个量时数字照样算得出来，但报告里要写明「不足以支撑结论」。这不是客套——一个 2 篇素材算出来的 100% 是噪声，把它当结论会让后面每一次调优都失去依据。

**分母只含已标注的素材。** 没进金标准集的篇，既不知道它有几条真结论，也不知道模型抽的对不对，算进来只会让分母变成一个说不清的东西。

### 4.8 原文检索（对 Q43 的一处修正）

原始决定是「不上向量库，用 SQLite 内置的 FTS5」。**实测之后前半句成立、后半句是错的。**

SQLite 的两个内置分词器在中文上都不适用：

| 分词器 | 搜「午门」 | 搜「只有午门」 |
|---|---|---|
| `unicode61` | **0 命中** | 0 命中 |
| `trigram` | **0 命中**（要求至少 3 个字符） | 1 命中 |

`unicode61` 把一整串连续汉字当成**一个词元**，所以「故宫只有午门能进，北门只出不进」只有整段照抄才命中；`trigram` 能子串匹配但两字词全查不到，而「午门」「故宫」「排队」「闭馆」恰恰是中文里最常见的查询词。

因此改为 **LIKE 子串扫描**。它在语义上恰好等于我们真正要问的问题——「这段原文里有没有这句话」——而且对任意长度的中文查询都准确。自用规模（数百到数千篇素材）下性能足够。

若日后素材量增长到需要索引，正确的升级路径是先接一个中文分词器把正文预切好，再喂给 `unicode61` 索引；直接上 FTS5 只会得到一个查不到两字词的索引。

检索入口在 `lushu/store/search.py`，其中 `document_contains()` 还承担一件事：**校验证据的原文片段是否真的存在于该素材里**。引用了原文中根本没有的话，等于没有溯源。

## 五、行程模型与排程

### 5.1 候选池

规划某座城市时，**候选池以攻略知识库为主、高德搜索补全**（Q27）。界面上先列出网友真正推荐过的地方，带打卡与避坑信息及置信度；高德负责补齐坐标与开放时间。知识库尚未覆盖的城市仍可直接搜高德。

排程不得引入候选池之外的景点——这条封闭世界约束沿用 FloatTrip，并由复审环节硬性检查。

### 5.2 排程流水线

沿用 FloatTrip 的编排（`third_party/floattrip`），扩展点如下：

| 环节 | 沿用 | 扩展 |
|---|---|---|
| 需求理解 | 对话式 Brief | Brief 容纳城市停留序列 |
| 景点搜索 | 高德 POI 搜索 | 候选池改为知识库优先 |
| 地理分区 | 确定性 k-means | **分区必须在城市停留内部执行**，否则会跨城横跳 |
| 排程 | Planner | prompt 注入硬约束 |
| 复审 | Reviewer | 增加「预约可行性」检查：该景点当天是否已过放票日 |
| 开放时间校验 | Time Check 专项 Agent | 增加闭馆日与预约规则 |
| 餐饮 | 按天并行加确定性降级 | 无 |
| 城际转移 | —— | **新增**：交通方式建议与备选方案 |
| 攻略挂载 | —— | **新增**：把软经验挂到天项上 |
| 预算 | —— | **新增**：市内与城际分栏统计 |
| 收尾 | finalize | 无 |

### 5.3 知识进入 LLM 的方式

两种信息分开走（Q32）：

- **注入 prompt 的是硬约束**——开放时间、闭馆日、放票日、是否必须预约、地理坐标、人流高峰时段的短摘要。LLM 需要这些信息才能排出可执行的行程。
- **不注入而是生成后挂载的是软经验**——完整的避坑指南与打卡建议原文。这样 LLM 无法把它们当成自己写的内容混进行程正文。

这是字段级分层采信（ADR-0001）的第二次生效。

### 5.4 城际转移

交通方式建议由**规则阈值加数据支撑**给出，不由 LLM 猜（Q33）：按距离与耗时阈值判断（如高铁 4 小时以内优先铁路，超过 6 小时或无铁路线路考虑航空），耗时与票价用 12306 实际数据支撑，LLM 只负责写一句推荐理由。

票价来源：12306 接口取火车实价，机票与大巴为估价并明确标注为参考价，用户可手动覆盖（Q14）。城际交通费在预算面板中独立成栏。

### 5.5 行程级信息

不从游记里生成可以套用的成品行程模板，但**抽取景点共现信号**（Q35）：两个景点常在同一天出现，说明它们地理或主题相近。这些共现关系累积起来是一份免费的、真实的景点邻近度先验，直接作为地理分区的输入，提升排程合理性。

## 六、景点预约子系统

### 6.1 规则库来源

**人工种子库加 LLM 抽初稿加人工复核**（Q10）。首期 20 至 30 个必须预约的国内景点，90 天复验一次（Q30）。入选标准是「不预约就真白跑」，宁可少而准——预约规则错一个字段，用户就会白跑一趟，这是本项目唯一会直接伤害用户的失败模式。

### 6.2 触达方式

三种，都不依赖应用常驻后台（Q11）：

1. 行程卡片上的醒目标注，含预约渠道与提前天数
2. 独立的预约清单页，把行程中所有需预约景点按距今剩余天数倒排
3. 导出 `.ics` 日历提醒，把提醒责任交给手机系统日历

### 6.3 复用

`reminders.js` 的 `computeReminders(startDate, [{item, leadDays}])` 与行程数据里的 `needsBooking`、`leadDays` 字段直接复用（MIT 许可）。注意它的仓库样例页已过时，不得作为反向工程的参考。

## 七、前端与交互

### 7.1 技术选型

- Vite + React + TypeScript（重新选，不沿用 FloatTrip 那套浏览器内 Babel 转译的无构建单页）
- Tailwind CSS + shadcn/ui（组件是拷进仓库而不是装成依赖）
- 应用内地图：高德 JS 地图 API

### 7.2 页面

| 页面 | 内容 |
|---|---|
| 对话页 | 主入口。城市序列与天数在此确认，读作对话式 |
| 行程编辑器 | 城市停留列表（增删、改天数）→ 逐日时间轴 → 天项拖拽换序、换点、改时间 → 相邻点移动方案 |
| 路线总览图 | 城市为节点、城际转移为边的拓扑视图。**它不是知识图谱** |
| 预算面板 | 市内与城际分栏，标注参考价 |
| 天气面板 | 按城市分别展示 |
| 预约清单 | 按剩余天数倒排的待办 |
| 数据工作台 | 待对齐、待复核、待标注三类队列 |
| 路书导出 | 生成单文件 HTML |

### 7.3 交互范式

**对话式为主**（Q31），但有一个明确分工（Q38）：

- 语义级变动走对话——加城市、删城市、换城市、改偏好、改节奏、提出新的约束
- 纯数值编辑走界面——改天数、改日期，改完直接触发重规划

理由是 LLM 解析「4」没有任何价值且有出错概率，而重规划该跑还是要跑。

### 7.4 破坏性操作的防护

对话触发的重规划会覆盖手工调过的顺序与餐厅（Q48）。防护是两条，都不需要版本历史系统：

1. 重规划前弹出「旧 → 新」差异，确认后才覆盖
2. 会话内的撤销与重做栈，外加离开页面前的未保存变更守卫

## 八、路书导出

产物是单个 HTML 文件，手机优先、离线可读，用于旅行途中在手机上查阅。

**不含交互地图，只保留导航深链**（ADR-0006）。因此页面必须用顺序、时间段与路段文字描述（距离、耗时、交通方式、起终点）来补偿空间关系的缺失，这块内容要做足。

复用 travel-plan-viz 的 `reminders.js`（预约清单）与 `validate.js`（契约校验），以及 `map.js` 中的导航深链构造函数；地图渲染部分不使用。生成后必须跑一次契约校验，有错误必须修复后重跑。

> **修订（M6 之后）**：这里原写的是复用上述三个文件。真正读到它们之后改成了自己写，
> 只有一项检查被采纳。逐条理由见下，以及第九节的复用清单。
>
> - **预约清单**：它是「出发日 − `leadDays`」，我们的是**每个景点各自的游览日**往回
>   倒推。多城市行程里这个差别要命——陕历博 11-16 游览、11-11 放票，按出发日 11-12
>   算会得出 11-05。何况我们还要带渠道、实名要求、闭馆日，以及「官方根本没公布
>   放票口径」这一态（`BookingRule.has_release_window`）。
> - **契约校验**：它的 `validate.js` 认的是它自己的契约——强制内嵌 Leaflet 在线地图
>   与 `trip-data` JSON。拿它校我们的路书会直接报 3 个 ERROR，而那 3 条正是
>   ADR-0006 明确放弃的东西。我们自己的契约有 12 个错误码，只认「手机离线打开」。
> - **采纳了一项**：它的坐标离群检测。原版按**全局中位点**比 3 度，跨城市行程会满屏
>   报警（南京到西安本身就差 10 度），所以改成**按城市**比 1.0 度（约 110 公里），
>   并补一条机械判定的越界检查，专抓经纬度写反。
>
> 校验的失败信息本身也得印得出来：Windows 控制台默认 GBK，`✗`（U+2717）不在 GBK 里，
> `print` 会抛 `UnicodeEncodeError`——**最该看见错误的时候看到的是 traceback**。
> 命令入口现在把不可编码的字符降级成 `?`（`tests/test_cli_console.py`）。

## 九、代码复用清单

### 从 FloatTrip 拷贝，隔离在 `third_party/floattrip/`（ADR-0005）

- 排程与复审编排：规划与复审循环、开放时间专项校验、候选池封闭世界的硬性检查
- 地理分区：固定种子的确定性聚类
- 模型接入层：供应商工厂与两个实现，配 `LLM_PROVIDER` 切换
- 实体适配器：高德 POI 搜索、周边搜索、天气
- 运行服务：Run 状态机、事件序号与断线回放、并发与锁、中断恢复
- 对话层：意图判定、Brief 状态机、上下文压缩、结构化输出修复重试
- 工程经验：架构边界测试、确定性计算优先于 LLM 评审的分层思路

**明确不搬**：任何二进制状态库、密钥文件、移动端工程、移动端原型、营销页面与图片、推广素材。这些不只是体积问题——那个仓库把 5.4MB 的检查点库和一份调试签名密钥提交进了版本控制。

同时记录出处：源仓库、提交哈希、拷贝日期、改动摘要。

### 借鉴 travel-plan-viz（MIT，不拷代码）

它的三个引擎文件都读过（`~/.claude/skills/travel-plan-viz/assets/`），一件都不适合
直接拷，只有一项检查被采纳——理由见第八节的修订：

- `reminders.js`：提醒口径是「出发日 − `leadDays`」，与我们的「按景点游览日倒推」
  不同，且不含渠道、实名、闭馆日与「放票口径未公布」这一态
- `validate.js`：只认它自己的契约（强制 Leaflet 在线地图 + `trip-data` JSON），
  与 ADR-0006 冲突；其中**坐标离群的思路**被采纳，判据按多城市行程重写
- `map.js`：不用。ADR-0006 不含地图，ADR-0003 全库统一 GCJ-02，不需要它那条
  GCJ-02 → WGS-84 的转换

### 只借鉴设计、不拷贝代码

- TREK（AGPL-3.0，抄代码有传染性风险）：地图引擎抽象层、离线缓存分级的思路
- Voyago（编排层无代码，实现不可复用）：行程节点树与路段方案对比的数据契约、「攻略仅作灵感、价格地址以 API 为准」的分层采信
- TripForge：无可复用内容

## 十一、风险与验证方式

| 风险 | 为什么致命 | 验证方式 | 出现时机 |
|---|---|---|---|
| 实体对齐准确率 | 对不上，攻略知识就挂不到行程上，产品价值归零 | 金标准集测对齐准确率；人工核对抽样 | M3 |
| 独立来源去重失效 | 置信度退化成转发量，整个信任模型是假的 | 构造转载样本集，验证同篇多站只计一个来源 | M3 |
| 提纯质量无金标准集 | 无法区分「提纯很准」与「只看到了准的那几条」，后续每次调优都是盲调 | 30 篇素材的人工标注集，跑三个指标 | M3 |
| 预约规则错误 | 唯一会直接让用户白跑一趟的失败模式 | 90 天复验扫描；每条规则必须有渠道来源链接 | M4 |
| 拷贝代码的许可不确定性 | 影响将来能否开源 | `third_party` 目录边界；业务层只通过薄适配调用 | 全程 |
| 攻略素材的版权与站点条款 | 影响数据来源可持续性 | 不碰登录态；全文只留本地底档；路书只带片段 | M3 |
| 多城市下分区跨城横跳 | 排出的行程不可执行 | 分区只在城市停留内部执行；对两城行程做回归 | M2 |
| 对话重规划覆盖手工调整 | 用户会不敢用对话改行程 | 差异确认弹窗；撤销栈；覆盖场景的回归测试 | M2 |
