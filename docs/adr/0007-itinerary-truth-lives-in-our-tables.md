# 行程数据的真相在本项目的表里，引擎只负责生成

## 背景与决策

vendored 引擎自己有一套行程持久化：`itineraries` 表存 `plan_json` 与 `planner_state_json`，`planning_briefs` 存规划前的结构化需求。本项目又有一套行程表：`trip → city_stay → day → day_item`。两者共存于同一个 SQLite 文件，因此必须回答一个问题——**行程以谁为准**。

决策：**本项目的表是行程的唯一真相。引擎的产出是「生成建议」，经转换写入本项目的表；引擎自己的 `itineraries` 表只作为生成过程的运行记录，不参与读取。**

三条理由：

1. **引擎的表支撑不了产品模型。** 它是单城市结构（`destination` 是一个字符串，`plan_json.days[]` 是扁平的天列表），而本项目的行程是「城市停留序列」，要在城市之间插入城际转移、要按城市分别统计预算与天气。把真相放在 `plan_json` 里，等于每次读行程都要从 JSON 里现算这些结构。
2. **真相的归属决定了引擎能否被替换。** ADR-0005 承诺 vendored 代码可丢弃、可替换。如果行程真相在它的表里，这个承诺就是假的——换掉引擎等于丢掉全部用户数据。
3. **引擎的写入路径带着隐式用户。** 它的表普遍有 `user_id NOT NULL REFERENCES users(id)`，而本项目没有账号体系。让自有表依附于这条外键，等于给一个不存在的东西让路。

## 后果

- **`plan_json` 不再被读取，只被写入。** 我们保存它作为生成过程的证据（用户想回看「AI 当时为什么这么排」时有用），但任何界面都不从它渲染行程。
- 转换层（引擎产出 → 自有表）是一次**有损且单向**的映射：引擎独有的概念（`reasoning`、`planner_reviewer_dialogue`、`history`）不进自有表，留在 `plan_json` 里按需查阅。
- 引擎重新生成行程时，是**替换**自有表里的天与天项，而不是追加。用户在转换之后做的手工调整会被覆盖，因此重规划必须先弹「旧 → 新」差异让用户确认（Q48）。
- 本项目自己的行程结构（城市停留、城际转移、天数口径）一旦需要演进，改动落在自有表与转换层，不必触碰 vendored 代码。
