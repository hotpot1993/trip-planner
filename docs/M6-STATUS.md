# M6 进度：路书导出

设计第八节：产物是**单个 HTML 文件，手机优先、离线可读**，旅行途中在手机上
查阅。验收条件是「手机上离线打开可用」。

---

## 一、已完成：契约层 + 装配 + 渲染

```
ls export <trip_id>              导出单文件 HTML 路书
ls export <trip_id> --check      只跑契约校验，不写文件
ls export                        列出可导出的行程
```

真实行程导出实测：**11 KB，零外部加载，可离线打开**。已在 390px 手机宽度下
截图核对。

| 层 | 文件 | 管什么 |
|---|---|---|
| 契约 | `lushu/domain/roadbook.py` | 「一份合格的路书必须有什么」 |
| 装配 | `lushu/services/roadbook_service.py` | 从库里装出来；路段估算 |
| 渲染 | `lushu/services/roadbook_render.py` | 渲染成单文件 HTML；离线自检 |
| 入口 | `ls export`、`scripts/export_roadbook.py` | 有错就不写文件 |

### 契约（`lushu/domain/roadbook.py`）

设计里明说「生成后必须跑一次契约校验，有错误必须修复后重跑」。契约要单独一层，
是因为设计写死了两条**会静默失败**的约束：

| 约束 | 错了会怎样 |
|---|---|
| 不含交互地图，只保留导航深链（ADR-0006） | 不会报错。空间关系全靠顺序、时间段与路段文字补偿——设计原话是「这块内容要做足」。缺了路段描述，在地图上看没问题，在手机上就是一堆地名 |
| 离线可读 | 不会报错。任何一条外部资源引用都会让它在大理到丽江的山路上变成半张白纸，而那恰恰是旅行的常态 |

错误项：引用了外部资源、日期不连续、相邻天项的时刻矛盾、路段数与天项数对不上、
预约条目没有渠道。提醒项：没有路段说明、只写怎么走没写多远多久、
没有导航深链、写着步行却太远、景点没有地址。

### 路段：没有地图，这段文字就是空间关系的全部载体

`leg_option` 表从 M1 起就是空的，所以这里按坐标算**直线距离**与预计耗时，
**并如实标注是估算**——在没有地图的页面上说「步行 20 分钟」，用户会当真；
说「直线约 1.2 公里，实际路程更长」，他才知道要留余量。

算不出坐标的（比如没有 `poi_id` 的餐饮项）**留空**，页面上写「这段路没有坐标，
到当地问一下」。在陌生城市里按编出来的路线走，比知道「这段没算出来」糟得多。
真实行程上有 7 处这样的空缺，契约会如实报出来。

### 渲染的三条硬约束

1. **零外部加载**：没有字体、没有 CDN、没有图片链接，样式全部内联
2. **手机优先**：窄屏单列、字号按手机阅读定——这份东西只有一种使用场景，
   站在路边低头看
3. **导航深链保留**：点开跳到地图 App，这是地图被砍掉之后留下的那部分

配色沿用主项目的青绿山水：石青是结构色，石绿是打卡，**朱砂只标三类
「会让你的计划落空」的信息**。

45 项测试（22 契约 + 23 装配渲染）。

## 二、一件必须先说清的事：`travel-plan-viz` 的复用没有落地

设计第 7 行与第 368 行写的是「复用 travel-plan-viz 的 `reminders.js`
（预约清单）与 `validate.js`（契约校验），以及 `map.js` 中的导航深链构造函数」。

**那个仓库没有进本项目。** `third_party/` 下只有 `floattrip`。

所以上面那份契约是**自己写的**，不是复用来的。这不是「忘了」，是一个需要
你定的岔路：

| 选择 | 代价 |
|---|---|
| 把 travel-plan-viz 也拷进 `third_party/`（照 ADR-0005 的先例） | 要先确认它的许可；它的数据结构与本项目未必对得上，可能要写一层转换 |
| 自己写（当前的选择） | 多写一份校验器；但规则是按本项目的失败模式定的——比如「离线可读」「路段描述要做足」这两条，是从本项目的设计约束反推出来的，未必是那个仓库的关切 |
| 不用那个仓库，但把它的规则读一遍再写 | 时间花在读上，收益不确定 |

我的判断是**自己写**，但这条决定该由你拍板——设计文档里白纸黑字写了「复用」，
现在实际不是，这个出入必须记在明处而不是悄悄绕过。

## 三、还没做

### 1. 真机验证

验收条件是「**手机上离线打开可用**」。目前只在 390px 宽度的无头浏览器里
核对过版式与外部引用，**没有真的传到手机上、开飞行模式打开一次**。
这一步得由你来做——它也是这个里程碑唯一算数的验证。

界面上的入口已经有了：行程页的「导出路书（单文件，可离线打开）」，
或者 `ls export <trip_id>`。

### 2. 路段的真实距离

现在用的是直线距离估算。高德有步行/驾车/公交路径规划接口，接上之后
距离与耗时就是真的，「这块内容要做足」才算做足。
要不要接是个取舍：多一次网络请求，换来路段可信。

### 3. 餐饮项没有坐标——**已修**

真实行程上路书有 7 处「这段路没有坐标，到当地问一下」，全部来自餐饮项。
根因不在路书，在**转换层**：引擎的餐饮环节是从高德周边搜索拿到的餐厅，
`restaurant_to_dict` 返回了 `location` 与 `address`，而我们的 `_convert_meal`
把它们一起丢了——只留下店名、时刻与理由。

丢的原因是没有地方存：天项的坐标原先只存在 `poi` 表里，靠 `day_item.poi_id`
指过去。这对景点成立（ADR-0002），但**给餐厅编一个 id 塞进 `poi` 表是错的**：
那会污染实体表，让餐厅出现在候选池与结论里。于是坐标只能丢。

迁移 10 让天项自己记一份：

```sql
ALTER TABLE day_item ADD COLUMN address TEXT;
ALTER TABLE day_item ADD COLUMN lat_gcj02 REAL;
ALTER TABLE day_item ADD COLUMN lng_gcj02 REAL;
```

坐标的取用顺序是「先实体、后天项」：景点仍以 `poi` 表为准（ADR-0001），
餐饮没有实体才退回天项自己那份。这是对 ADR-0001 的补充而不是违背——
记的是「这个地方在哪儿」，来源仍然是官方接口。

顺带修掉一个**同一根因的第二处**：`_item_from_row` 原先只在 `poi_id` 非空时
才建 `facts`，于是餐饮的坐标被读出来又丢掉。路书直接查库所以看不出，
**界面上却拿不到「这家店在哪」**。现在「有没有事实」由有没有事实决定，
不是由有没有实体 id 决定。

真实规划端到端验证：7 个天项 7 个有坐标（含 2 个餐饮项），
**路书契约从 7 处提醒降到 0**。两条读取路径都核对过：
路书直接查库、界面走 `load_trip`。

## 四、下一步建议

1. **真机验证**——M6 的验收条件只有真机能验
2. **让天项与结论共用一次对齐**（见 `docs/M5-STATUS.md` 第四节第 2 条）——
   现在中山陵与明孝陵的结论在行程上完全看不见，因为同一个地方在库里是两行

工作台 → 预约 → 候选池 → 城市页 → 软经验 → 路书导出，整条链在真实数据上
跑得通。剩下的三类事：接得更深的（候选池驱动排程、路径规划）、
需要真机验的（离线打开）、以及只能人来做的（标注 30 篇、复核规则）。
