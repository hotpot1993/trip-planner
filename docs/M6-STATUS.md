# M6 进度：路书导出

设计第八节：产物是**单个 HTML 文件，手机优先、离线可读**，旅行途中在手机上
查阅。验收条件是「手机上离线打开可用」。

---

## 一、已完成：契约层 + 装配 + 渲染

```
ls export <trip_id>              导出单文件 HTML 路书
ls export <trip_id> --check      只跑契约校验，不写文件
ls export                        列出可导出的行程
```

真实行程导出实测：**11 KB，零外部加载，可离线打开**。已在 390px 手机宽度下
截图核对。

| 层 | 文件 | 管什么 |
|---|---|---|
| 契约 | `lushu/domain/roadbook.py` | 「一份合格的路书必须有什么」 |
| 装配 | `lushu/services/roadbook_service.py` | 从库里装出来；路段估算 |
| 渲染 | `lushu/services/roadbook_render.py` | 渲染成单文件 HTML；离线自检 |
| 入口 | `ls export`、`scripts/export_roadbook.py` | 有错就不写文件 |

### 契约（`lushu/domain/roadbook.py`）

设计里明说「生成后必须跑一次契约校验，有错误必须修复后重跑」。契约要单独一层，
是因为设计写死了两条**会静默失败**的约束：

| 约束 | 错了会怎样 |
|---|---|
| 不含交互地图，只保留导航深链（ADR-0006） | 不会报错。空间关系全靠顺序、时间段与路段文字补偿——设计原话是「这块内容要做足」。缺了路段描述，在地图上看没问题，在手机上就是一堆地名 |
| 离线可读 | 不会报错。任何一条外部资源引用都会让它在大理到丽江的山路上变成半张白纸，而那恰恰是旅行的常态 |

错误项：引用了外部资源、日期不连续、相邻天项的时刻矛盾、路段数与天项数对不上、
预约条目没有渠道。提醒项：没有路段说明、只写怎么走没写多远多久、
没有导航深链、写着步行却太远、景点没有地址。

### 路段：没有地图，这段文字就是空间关系的全部载体

`leg_option` 表从 M1 起就是空的，所以这里按坐标算**直线距离**与预计耗时，
**并如实标注是估算**——在没有地图的页面上说「步行 20 分钟」，用户会当真；
说「直线约 1.2 公里，实际路程更长」，他才知道要留余量。

算不出坐标的（比如没有 `poi_id` 的餐饮项）**留空**，页面上如实说——不编路线。
在陌生城市里按编出来的路线走，比知道「这段没算出来」糟得多。

**但要说给读这一页的人听。** 原先写的是「这段路没有坐标，到当地问一下」：
那是给作者看的，而这一页是旅行途中在手机上翻的。实测一份路书里这样的句子
有 7 处，句子之间长得一模一样，读的人既不知道说的是哪儿，也不知道该干什么。
现在每条点名目的地并给出动作：「到「绿柳居」：没有坐标，按名字问路」。
契约里那条 `leg_missing` 仍然报给作者——**同一件事，给读者的话与给作者的话
不是同一句**。

### 渲染的三条硬约束

1. **零外部加载**：没有字体、没有 CDN、没有图片链接，样式全部内联
2. **手机优先**：窄屏单列、字号按手机阅读定——这份东西只有一种使用场景，
   站在路边低头看
3. **导航深链保留**：点开跳到地图 App，这是地图被砍掉之后留下的那部分

配色沿用主项目的青绿山水：石青是结构色，石绿是打卡，**朱砂只标三类
「会让你的计划落空」的信息**。

45 项测试（22 契约 + 23 装配渲染）。

## 二、`travel-plan-viz` 的复用：已定，只采纳一项

设计第 7 行与第 368 行原先写的是「复用 travel-plan-viz 的 `reminders.js`
（预约清单）与 `validate.js`（契约校验），以及 `map.js` 中的导航深链构造函数」。

**那个仓库当初没有进本项目**（`third_party/` 下只有 `floattrip`），所以上面那份
契约是**自己写的**。这一条当时记在这里等你拍板——现在它以 skill 的形式装上了
（`~/.claude/skills/travel-plan-viz/`），于是把三个文件都读了，逐条对照之后定的结果是：

| 它的资产 | 结论 |
|---|---|
| `reminders.js` | 不采纳。口径是「出发日 − `leadDays`」，我们是**按景点各自的游览日倒推**；多城市行程里按出发日算会错（陕历博 11-16 游览 → 11-11 放票，按出发日 11-12 算出 11-05）。且不含渠道、实名、闭馆日与「放票口径未公布」这一态 |
| `validate.js` | 契约部分不采纳（强制 Leaflet 在线地图 + `trip-data` JSON，与 ADR-0006 直接冲突，拿它校我们的路书会报 3 个 ERROR）。**采纳其中坐标离群检测的思路**，判据按多城市行程重写：按城市比 1.0 度而不是按全局中位点比 3 度，另加一条越界检查抓经纬度写反 |
| `map.js` | 不采纳。ADR-0006 不含地图；ADR-0003 全库统一 GCJ-02，不需要它那条 GCJ-02 → WGS-84 转换 |

设计文档第 7 行、第 368 行与第九节的复用清单已改成实际做法（含上述理由）。

顺带撞出并修掉一个更值得记的 bug：**契约校验发现 ERROR 时会打印 `✗`，而 Windows
控制台默认 GBK，`✗`（U+2717）不在 GBK 里，`print` 直接抛 `UnicodeEncodeError`。**
于是「有错误必须修复后重跑」这条路上，人看到的是一串 traceback，错误内容一个字都
没印出来。命令入口现在把不可编码的字符降级成 `?`，消息一个字不动
（`tests/test_cli_console.py` 钉住了它）。

## 三、还没做

### 1. 真机验证

验收条件是「**手机上离线打开可用**」。目前只在 390px 宽度的无头浏览器里
核对过版式与外部引用，**没有真的传到手机上、开飞行模式打开一次**。
这一步得由你来做——它也是这个里程碑唯一算数的验证。

界面上的入口已经有了：行程页的「导出路书（单文件，可离线打开）」，
或者 `ls export <trip_id>`。

### 2. 路段的真实距离

现在用的是直线距离估算。高德有步行/驾车/公交路径规划接口，接上之后
距离与耗时就是真的，「这块内容要做足」才算做足。
要不要接是个取舍：多一次网络请求，换来路段可信。

### 3. 餐饮项没有坐标——**已修**

真实行程上路书有 7 处「这段路没有坐标，到当地问一下」，全部来自餐饮项。
根因不在路书，在**转换层**：引擎的餐饮环节是从高德周边搜索拿到的餐厅，
`restaurant_to_dict` 返回了 `location` 与 `address`，而我们的 `_convert_meal`
把它们一起丢了——只留下店名、时刻与理由。

丢的原因是没有地方存：天项的坐标原先只存在 `poi` 表里，靠 `day_item.poi_id`
指过去。这对景点成立（ADR-0002），但**给餐厅编一个 id 塞进 `poi` 表是错的**：
那会污染实体表，让餐厅出现在候选池与结论里。于是坐标只能丢。

迁移 10 让天项自己记一份：

```sql
ALTER TABLE day_item ADD COLUMN address TEXT;
ALTER TABLE day_item ADD COLUMN lat_gcj02 REAL;
ALTER TABLE day_item ADD COLUMN lng_gcj02 REAL;
```

坐标的取用顺序是「先实体、后天项」：景点仍以 `poi` 表为准（ADR-0001），
餐饮没有实体才退回天项自己那份。这是对 ADR-0001 的补充而不是违背——
记的是「这个地方在哪儿」，来源仍然是官方接口。

顺带修掉一个**同一根因的第二处**：`_item_from_row` 原先只在 `poi_id` 非空时
才建 `facts`，于是餐饮的坐标被读出来又丢掉。路书直接查库所以看不出，
**界面上却拿不到「这家店在哪」**。现在「有没有事实」由有没有事实决定，
不是由有没有实体 id 决定。

**后来又发现：修好算法不等于修好数据。** 迁移不回填历史数据，上面那 7 处
空洞一个都没少——**7 个餐饮项的坐标全是空的**。于是补了 `ls trip coords`
（`lushu/services/meal_coords.py`）：默认只报不改，按名到高德查一遍，
只写分得清的那些。

两轮范围，两轮都跑过真机：

| 做法 | 结果 |
|---|---|
| 只按城市按名搜 | 查到 1 个（回味鸭血粉丝汤，唯一同名店，离夫子庙 200 米），6 个定不下来，**空洞 7 处一个没少** |
| 加上「绕着当天景点搜」 | 又查到 1 个（子午路张记肉夹馍，陕历博 1.8 公里外的分店），**空洞 7 → 6** |

第二轮的判据是有来历的：这些店名本来就是引擎按当天景点做**周边搜索**拿到的
（`meal_search_node` 用 `search_around_pois_async`），所以它们的落点也在那一片。
为此给 `adapters/poi.py` 加了周边搜索（`search_around_pois`，`place/around`），
顺手把三处重复的请求与错误处理收成一个 `_get_payload`——**一个接口的失败
不该长得跟另一个不一样**。

剩下的 5 个是判据**故意**不补的：

| 餐饮名 | 为什么定不下来 |
|---|---|
| 南京大牌档（中山陵店） | 高德上叫「南京大牌档(中山陵紫金坊店)」，名字差得远（0.576） |
| 蒋有记锅贴 | 最像的是「蒋有记(老门东店)」（0.3429） |
| 绿柳居 | 8 家同分（如「绿柳居(许府巷店)」）；绕着夫子庙、老门东搜仍然多家同分（品牌名不带分店，本来就不该猜） |
| 老孙家泡馍 | 4 家同分；周边同样 |
| 临潼石榴汁与 biangbiang 面 | 不是店名，是一串菜名（见下） |

**「一段路要两个端点都有坐标才算得出来」**——所以补一个点常常不减少一处
空洞。剩下这 5 个要么人工指定（人知道说的是哪一家），要么就不补。

**这 5 个不是判据没调好，是本来就不唯一。** 实测把候选摊开来看：

| 餐饮名 | 城市范围 | 夫子庙/城墙周边 3 公里 |
|---|---|---|
| 绿柳居 | 24 家，全部 0.9 分 | **仍然 5 家**（太平南路总店、老门东店、瑞金路店、熙南里店、夫子庙店） |
| 老孙家泡馍 | 25 家，其中**同名 1.0 分的 4 家** | 同名 1.0 分的还有 3 家 |
| 蒋有记锅贴 | 2 家，最好的是「蒋有记(老门东店)」0.3429 | 同样两家 |

所以**不要为了让数字好看去放宽阈值**。这三条的形状是一样的：行程里写的是
「品牌 + 菜名」（蒋有记锅贴、临潼石榴汁与 biangbiang 面），高德上写的是
「品牌 + 分店」（蒋有记(老门东店)、南京大牌档(中山陵紫金坊店)）——
靠字面分永远对不齐，靠「离得最近的那家赢」则会在一堆真分店里挑错一个。

### 4. 人工指定餐饮分店——**已做**

正确的做法是**让人来指定**，现在有了：行程页上「没有坐标的餐饮项」一块，
点开某一项就摊出候选，按「名字像不像、再按离当天景点多远」排好。

真实的账最能说明它为什么有用：`绿柳居` 在城里 17 个候选全都 0.90 分，
但按距离排下来第一行是**离老门东 96 米**的老门东店——而当天的行程就是
夫子庙与老门东。人一眼就认出是哪一家，机器永远认不出。

三处刻意的取舍：

- **列待办不联网**，候选单独一个接口、点开才取。一次页面加载打十几次外部
  接口，用户会以为界面卡死，额度也白烧。
- **不按名字分筛候选**。「蒋有记(老门东店)」只有 0.34，可它就是答案；
  筛掉它等于把答案藏起来。
- **距离是算出来的，与「哪次搜索找到它」无关**。第一版把距离绑在「是哪处
  锚点的周边搜索带回来的」，于是城市搜索来的候选全显示「距离算不出」——
  而我们手里明明有坐标。

排序也订正过一次：**距离不能单独当主序**。第一版只按距离排，截图一看，
搜「南京大牌档（中山陵店）」时紫金坊边上的火烧店、面馆全排在了真分店前面
（它们离得更近）。现在名字分是主序、距离是次序，两种真实情形都对：
品牌名不带分店时同分、距离说话；高德名字与行程写的不一样时分数都低、
距离仍然说话。

**「临潼石榴汁与 biangbiang 面」这一条差点写错。** 它按包含关系命中了
「biangbiang面」那家店（名字分 0.90，过了及格线），而那家店在城北未央路，
**离兵马俑 35 公里**——写进去就成了「从兵马俑走 35 公里去吃面」。
现在有一道「这不像店名」的关（名字里有「与 / 、/ ＋/ +」的多半是一串菜名；
「和」刻意留着，否则「永和豆浆」会被判成菜名）。

过程里撞出并修掉的另外两处，都是同一类错——**读了一处，而别处读的是两处**：

- **锚点取不到。** 第一版周边搜索的锚点只查 `day_item.lat_gcj02`，而历史行程的
  景点坐标一直在 `poi` 表里（迁移 10 才让天项自己记）。表现是「周边搜索一次
  都没跑」，屏幕上完全看不出为什么。现在按「先实体、后天项」取，
  与 `roadbook_service`、`trip_store._load_day` 同一条规矩。
- **报出来的原因说了假话。** 「算结果」与「算理由」各写了一遍，于是
  「对上了但高德没给坐标」只有一边知道，报出来成了「有 1 家同分的店」
  （一家怎么会同分）。现在结论与理由出自同一个 `_decide`。

还有一处：周边搜索的异常原先接的是 `Exception`，于是注入的搜索函数写错签名
也会显示成「高德搜索失败：unexpected keyword argument」——那是我们的 bug，
该炸就炸。现在只接 `PoiSearchError`，与 `pipeline._fetch_from_db` 一致。

**最后一条不是代码的错，是抄的错。** 上面那张表里的店名，第一版有四个是错的：
「回味鸭血粉丝汤」抄成「鸭血粉丝汤」、「蒋有记锅贴 / 蒋有记(老门东店)」抄成
「许记糕点 / 许记(许家巷店)」、「中山陵紫金坊店」抄成「中山陵金陵店」。
根因是从**控制台乱码**里认字——本机的控制台是 GBK，`ls` 的输出在这儿显示成
一串问号方块，我按上下文猜了字形。凡是中文标识符（店名、景点名、地名），
**写进文件再用读文件的方式看**，不要从终端输出里抄。

真实规划端到端验证：7 个天项 7 个有坐标（含 2 个餐饮项），
**路书契约从 7 处提醒降到 0**。两条读取路径都核对过：
路书直接查库、界面走 `load_trip`。

## 四、下一步建议

1. **真机验证**——M6 的验收条件只有真机能验
2. **让天项与结论共用一次对齐**（见 `docs/M5-STATUS.md` 第四节第 2 条）——
   现在中山陵与明孝陵的结论在行程上完全看不见，因为同一个地方在库里是两行
3. 回到数据：金标准集标到 30 篇、预约规则补到 30 条

到这一步，M0–M6 的**代码**部分齐了：导入 → 提纯 → 归组 → 对齐 → 评测 →
工作台 → 预约 → 候选池 → 城市页 → 软经验 → 路书导出，整条链在真实数据上
跑得通。剩下的三类事：接得更深的（候选池驱动排程、路径规划）、
需要真机验的（离线打开）、以及只能人来做的（标注 30 篇、复核规则）。
