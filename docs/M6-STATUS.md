# M6 进度：路书导出

设计第八节：产物是**单个 HTML 文件，手机优先、离线可读**，旅行途中在手机上
查阅。验收条件是「手机上离线打开可用」。

---

## 一、已完成：契约层

`lushu/domain/roadbook.py` 定义的**不是渲染器，是契约**——先把「一份合格的
路书必须有什么」写成可检查的规则，渲染器照着它产出，生成之后再跑一遍校验。
设计里明说「生成后必须跑一次契约校验，有错误必须修复后重跑」。

契约要单独一层，是因为设计写死了两条**会静默失败**的约束：

| 约束 | 错了会怎样 |
|---|---|
| 不含交互地图，只保留导航深链（ADR-0006） | 不会报错。空间关系全靠顺序、时间段与路段文字补偿——设计原话是「这块内容要做足」。缺了路段描述，在地图上看没问题，在手机上就是一堆地名 |
| 离线可读 | 不会报错。任何一条外部资源引用（字体、图片、CDN）都会让它在大理到丽江的山路上变成半张白纸，而那恰恰是旅行的常态 |

校验项（错误 → 这份东西不能发到手机上）：

- 引用了外部资源
- 日期不连续 / 首尾与出发结束日期对不上
- 相邻天项的次序与时刻矛盾（顺序是「用文字补偿空间关系」的前提）
- 路段数与天项数对不上
- 预约条目没有渠道（用户知道要预约却无处可去）

提醒项（能用，但该补）：

- 两处之间没有路段说明 / 只写了怎么走没写多远多久 / 没有导航深链
- 写着步行但超过 800 米
- 景点没有地址

22 项测试，全绿。

## 二、一件必须先说清的事：`travel-plan-viz` 的复用没有落地

设计第 7 行与第 368 行写的是「复用 travel-plan-viz 的 `reminders.js`
（预约清单）与 `validate.js`（契约校验），以及 `map.js` 中的导航深链构造函数」。

**那个仓库没有进本项目。** `third_party/` 下只有 `floattrip`。

所以上面那份契约是**自己写的**，不是复用来的。这不是「忘了」，是一个需要
你定的岔路：

| 选择 | 代价 |
|---|---|
| 把 travel-plan-viz 也拷进 `third_party/`（照 ADR-0005 的先例） | 要先确认它的许可；它的数据结构与本项目未必对得上，可能要写一层转换 |
| 自己写（当前的选择） | 多写一份校验器；但规则是按本项目的失败模式定的——比如「离线可读」「路段描述要做足」这两条，是从本项目的设计约束反推出来的，未必是那个仓库的关切 |
| 不用那个仓库，但把它的规则读一遍再写 | 时间花在读上，收益不确定 |

我的判断是**自己写**，但这条决定该由你拍板——设计文档里白纸黑字写了「复用」，
现在实际不是，这个出入必须记在明处而不是悄悄绕过。

## 三、还没做

### 1. 渲染器

把 `Roadbook` 渲染成单个 HTML 文件：内联 CSS、无外部请求、手机优先。
难点不在 HTML，在于**「这块内容要做足」**——没有地图，怎么用文字把
「上午故宫、步行二十分钟到景山、傍晚上城墙」讲清楚。

### 2. 从行程装配 `Roadbook`

`lushu/domain/roadbook.py` 里的数据结构是手写的，还没有从
`StoredTrip` + 预约清单 + 软经验装配出来的那一步。
路段（`legs`）尤其没有来源——`leg_option` 表在本项目里一直是空的，
它是从 Voyago 借鉴来的结构，M1/M2 没填过。所以「路段描述」这一块
要么接一个路径规划接口，要么先用直线距离与交通方式估。

### 3. 导航深链

设计说从 `map.js` 借「导航深链构造函数」。高德的 URI API 形态是
`https://uri.amap.com/marker?position=lng,lat&name=...` 与
`/navigation?from=...&to=...`。这一步要连坐标一起处理，而 M2 落库的
14 条 POI 里坐标是有的、`typecode` 与 `parent_poi_id` 是空的（M3 已补齐）。

### 4. 导出接口与 CLI

`GET /api/trips/{id}/roadbook.html` 与 `ls export <trip_id>`。
