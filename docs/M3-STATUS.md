### 代码分层


## 二、未完成

按对 M3 验收条件的贡献排序：

### 1. 金标准集与评测（`ls eval gold` / `ls eval run`）

这是 M3 完成标志里唯一还缺的东西，也是设计里点名的风险
「提纯质量无金标准集，后续每次调优都是盲调」。

要做三件事：

- **标注界面**：`lushu/api/workbench_routes.py` 已有 `gold_label` 表但没接口。
  标注的交互形状与待对齐一样（Q47），所以工作台页面可以复用同一套组件
- **匹配算法**：预测的结论与人工标注怎么算命中。要按「主体 + 事实点」比，
  不是按文本相似度——模型把「只有午门能进」写成「午门是唯一入口」仍然算命中
- **三个指标**：精确率、召回率、对齐准确率。前两个来自标注集，
  第三个用 `alignment_task` 上人工处置过的结果回流

### 2. 数据工作台界面（前端）

`web/src/` 目前只有行程相关的视图。工作台要新增：

- 三类队列共用一个页面的形状（Q47）
- 待对齐：左侧候选结论全文 + 原文片段，右侧高德候选与拒绝理由
- 提纯概览：`dropped_count` 不为零的篇要突出——那是模型编引文的信号
- 结论列表：置信度、独立来源数、证据可展开

不要忘记设计里的一条：**界面上要标注而不是隐藏**过期的经验（Q49）。

### 3. 导入与管线的接口

`workbench_routes.py` 只做了读与处置。还缺：

- `POST /api/ingest`（粘贴导入）
- `POST /api/pipeline/run`（触发一轮，SSE 报进度，形状参考
  `lushu/api/plan_routes.py` 的 `POST /api/plan/stream`）

### 4. 第二层归组的真实数据验证

`group_by_conclusions` 只在小样本上测过。真实素材库里「逐句改写」
长什么样还没见过——阈值 0.80 是按推理定的，不是实测定的。

### 5. 复验扫描（`ls verify scan`）

设计把它放在 M7，但 `claim.verify_due_at` 已经在算了。
可以先做一个只读的清单，让人看得见哪些结论快过期。

## 三、动手过程中踩到的坑（都已修）

| 症状 | 根因 | 教训 |
|---|---|---|
| 对齐准确率只有 14% | 判断「本体还是子点」需要父节点，而父节点经常不在搜索结果里 | 外部数据的层级关系要主动补全，不能假设它在结果里 |
| 对齐 14/14 通过，结论一条也写不进去 | `claim.poi_id` 有外键，对齐成功时没把 POI 写进 `poi` 表 | **纯函数测通 ≠ 端到端跑通**，真实路径必须跑一次 |
| 排序分全都一样，差值恒为 0 | `min(score + bonus, 1.0)` 把加成夹掉了 | 排序分的上界不要夹，它只是排序用的 |
| 另一个测试报外键失败，根因在几十行外 | `with connect(db) as conn:` **退出时不提交** | 已钉成 `tests/test_store_transaction_discipline.py` |
| 工作台页面 500 | 库里存着早先版本的 JSON 形状 | 对库里的 JSON 不能盲信 |
| 城市挂载撞外键 | 高德给区县级 adcode，`city` 表存市级 | 层级不同要先归档，找不到就报错 |

## 四、下一步建议

按设计里风险表的排序，**先做金标准集**。理由：

1. 它是 M3 完成标志里唯一还缺的
2. 没有它，`facet` 标注不准、第二层归组阈值合不合适、抽取质量到底如何
   ——这三个问题都只能靠感觉（`M3-PROBE.md` 1.2 节已经明确写了
   「金标准集跑起来之前调它就是盲调」）
3. 它需要的接口（`gold_label` 表的读写）与待对齐的接口形状几乎一样，
   工作台页面可以一次做完两类队列

界面可以稍后——数据链路是自用工具，`ls` 命令已经能跑完整条链，
界面的价值在「处置待对齐」这类重复劳动上，那些队列现在还没攒起来。
